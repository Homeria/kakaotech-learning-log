### 1. DOM(Document Object Model)과 이벤트
- 다양한 종류의 tag가 있는 HTML, 방대한 양의 꾸미기 속성이 있는 CSS, 타입이 엄격하지 않고 함수조차 object로 취급되는 js와의 싸움을 이겨내고 본격적으로 프론트엔드다운 설계에 들어가기 위한 기초 내용이다.
- DOM은 Tree 형태로 루트, 부모, 자식, 노드의 개념을 그대로 사용한다. 태그 하나를 노드라고 보고, 태그 안에 태그를 자식으로 취급한다.
- document 객체를 통해 오브젝트에 접근할 때는 다음의 방법으로 접근할 수 있다.

    | 구분 | 메서드 | 반환 대상 |
    |---|---|---|
    | 하나 선택 | `getElementById()` | 특정 id의 요소 하나 |
    | 하나 선택 | `querySelector()` | CSS 선택자에 맞는 첫 번째 요소 |
    | 모두 선택 | `getElementsByTagName()` | 특정 태그의 모든 요소 |
    | 모두 선택 | `getElementsByClassName()` | 특정 class의 모든 요소 |
    | 모두 선택 | `getElementsByName()` | 특정 name 속성값의 모든 요소 |
    | 모두 선택 | `querySelectorAll()` | CSS 선택자에 맞는 모든 요소 |

- 오브젝트에 접근해서 요소를 변경하는 방법에는 다음이 있다.

    | 사용 예시 | 설명 |
    |---|---|
    | `요소.style.스타일속성 = "200px"` | 요소의 스타일 조회 및 변경 |
    | `요소.innerHTML = "<li><span>hello</span></li>"` | 요소 하위의 HTML 조회 및 변경 |
    | `요소.innerText = "Hello Elice"` | 요소 하위의 텍스트 조회 및 변경 |
    | `요소.getAttribute("placeholder")` | 요소의 HTML 속성 조회 |
    | `요소.setAttribute("min", "20")` | 요소의 HTML 속성 변경 |
    | `요소.classList` | 요소의 class 수정 |

- 요소를 생성하고 추가하는 방법은 다음이 있다.

    | 메서드 사용 예시 | 설명 |
    |---|---|
    | `document.createElement("form")` | 해당 태그의 HTML 요소를 생성 |
    | `document.write("Hello World")` | 텍스트를 화면에 출력 |
    | `요소.appendChild(node)` | 해당 요소 내부 가장 마지막에 node 추가 |

- 이벤트는 HTML 요소에 대한 사건의 발생을 의미하며, 종류에는 다음이 있다.

    | 이벤트 종류 | 설명 |
    |---|---|
    | 마우스 이벤트 | 마우스 조작과 관련된 이벤트 |
    | 키 이벤트 | 키보드 조작과 관련된 이벤트 |
    | 폼 이벤트 | `form` 태그 관련 동작에 대한 이벤트 |
    | 로드 관련 이벤트 | 페이지나 리소스가 로드될 때 발생하는 이벤트 |
    | 창 관련 이벤트 | 브라우저 창 크기 변경 등과 관련된 이벤트 |

- 이벤트 핸들러는 이벤트가 발생하면 특정 동작을 수행한다. 즉, 이벤트가 트리거가 된다.
- 이벤트 핸들러의 등록 방법은 다음과 같다.

    | 방법 | 설명 | 권장 여부 |
    |---|---|---|
    | HTML 속성에 등록 | HTML 요소의 `on이벤트명` 속성에 직접 동작을 추가 | 권장되지 않음 |
    | node 객체 프로퍼티에 등록 | node 객체의 `on이벤트명` 프로퍼티에 함수 등록 | 사용 가능 |
    | `addEventListener()` 사용 | 이벤트명과 핸들러 함수를 인수로 전달 | 권장 |

- 이벤트 핸들러의 제거는 removeEventListener() 메서드를 사용한다.

- event 객체는 이벤트 핸들러 함수에 첫 번째 인수로 전달되는 객체로, 이벤트에 대한 정보를 담고 있다. 

    | event 객체 종류 | 설명 |
    |---|---|
    | 마우스 이벤트 | 마우스 위치, 클릭 정보 등 |
    | 키 이벤트 | 누른 키에 대한 정보 등 |
    | 이벤트 타겟 | 이벤트가 실제로 발생한 대상 요소의 node 객체 |
    | preventDefault | form 태그에서 submit 버튼의 기본 동작을 차단 |

- 이벤트는 DOM 트리에 따라 전파되는데, 이를 이벤트 전파라고 한다.
- 예를 들어, 이벤트는 가장 하위 요소에서 버튼 클릭 이벤트가 발생했을 때 그 이벤트는 DOM 트리를 통해 여러 상위 요소로 전달된다.
- 이러한 이벤트 전파는 크게 세 단계로 나눌 수 있다.

    | 단계 | 설명 |
    |---|---|
    | Capturing Phase | 이벤트가 상위 요소에서 하위 요소 방향으로 내려가는 단계 |
    | Target Phase | 이벤트가 실제 대상 요소에 도달한 단계 |
    | Bubbling Phase | 이벤트가 대상 요소에서 상위 요소 방향으로 올라가는 단계 |

- Bublling Phase의 경우에는 부모 요소의 이벤트 핸들러까지도 실행될 수 있으므로, 이를 막고 싶다면 event.stopPropagation()을 사용하여 전파를 차단한다.

- 사실 DOM과 이벤트 관련해서는 크게 어렵지 않았다. 암기할 게 많을 뿐이다... JS가 자유도가 높은 언어인 만큼 기상천외한 방식으로 동작하는 듯 해 보인다. 그래서 타입스크립트가 만들어진 게 아닌가 싶다..

### 2. ES6와 비동기

- JS는 시대를 거쳐오며 많은 문법 변화들이 이루어졌다. 주요 문법으로는 다음이 있다.

    | 문법 | 예시 | 설명 |
    |---|---|---|
    | `let`, `const` | `let name = "Elice";` | 변수를 선언하는 새로운 방식 |
    | 화살표 함수 | `() => { ... }` | 함수를 간결하게 작성하는 문법 |
    | 구조 분해 할당 | `const { name, age } = user;` | 객체나 배열의 값을 쉽게 변수에 할당 |
    | Spread 문법 | `const arr = [...arr1, ...arr2];` | 배열이나 객체를 펼쳐서 사용 |
    | 템플릿 리터럴 | `` `Hello ${name}` `` | 문자열 안에 변수나 표현식을 쉽게 삽입 |
    | 옵셔널 체이닝 | `user.contact?.email` | 존재하지 않는 값에 안전하게 접근 |
    | 프로퍼티/메서드 축약 | `{ name, age }` | 객체 작성 시 중복을 줄이는 문법 |
    | 배열 메서드 | `forEach`, `map`, `filter`, `reduce` | 배열 데이터를 효율적으로 처리 |

- 변수 선언으로는, 불변일 경우 `const`, 가변일 경우 `let`을 사용한다.
- `var`의 경우에는 특이하게도 함수 레벨 스코프를 지원하며, `if`문 내부에서 선언한 변수는 블록 밖에서도 접근될 수 있다. 블록 안에서 전역 변수를 선언한 것과 같은 효과인 셈인건가?

- 문자열 연결로는 `+` 연산이 있지만, 템플릿 리터럴로 하면 "" 또는 ''로 감싸던 걸 ``로 수정하고 `${변수명}` 형식으로 쓰면, python의 `f"{변수명}"` 형식과 비슷하게 동작한다.

- 배열 메서드 종류로는 다음이 있다.
    - 고차 함수 : 함수를 인자로 받거나 함수를 반환하는 함수
    - 콜백 함수 : 함수를 인자로 받는 고차 함수에서, 인자로 넘겨주는 함수
         | 메서드 | 설명 |
        |---|---|
        | `forEach` | 각 요소에 대해 콜백 함수를 한 번씩 실행 |
        | `map` | 각 요소를 변환하여 새로운 배열 반환 |
        | `filter` | 조건을 만족하는 요소만 모아 새로운 배열 반환 |
        | `reduce` | 각 요소를 누적 계산하여 하나의 결과 반환 |

- js에서는 내장 객체가 존재하며, 종류로는 다음이 있다.

    | 객체 | 설명 |
    |---|---|
    | `window` | 브라우저 창을 나타내는 객체 |
    | `document` | 브라우저에 로드된 웹 페이지 객체 |
    | `Number` | 숫자 자료형을 다루기 위한 객체 |
    | `Math` | 수학 연산과 상수를 제공하는 객체 |
    | `Date` | 날짜와 시간을 다루기 위한 객체 |
    | `String` | 문자열을 조작하기 위한 객체 |
    | `JSON` | 객체를 직렬화/역직렬화하기 위한 객체 |

- js 코드는 js 엔진을 통해 파싱되고 실행되는데, Chrome에서는 V8 엔진을 사용한다.
- 엔진은 코드 실행 전에 실행 컨텍스트를 생성하는데, 이는 코드가 실행되는 환경을 정의하며, 변수, 함수 선언, this 바인딩 등의 실행에 필요한 정보를 관리하는 개념이다.

    | 단계 | 설명 |
    |---|---|
    | 생성 단계 | 변수 선언문과 함수 선언 등을 먼저 저장 |
    | 실행 단계 | 나머지 코드를 실행하고 변수 값 할당 |

- 실행 컨텍스트는 콜 스택(Call Stack)에서 관리된다.

- js는 단 하나의 콜 스택을 가지기 때문에, 싱글 스레드 기반 언어라고 할 수 있다.

- 싱글 스레드는 진행 중인 작업이 종료되기 전까지는 이후 작업을 시작하지 못하는 블로킹 문제가 발생하며, 이를 해결하기 위해 처리 방식을 달리하여 동기/비동기로 방식을 나눌 수 있다.

    | 구분 | 동기 처리 | 비동기 처리 |
    |---|---|---|
    | 실행 방식 | 순차적으로 실행 | 작업 완료를 기다리지 않고 다음 작업 실행 |
    | 대기 여부 | 현재 작업이 끝날 때까지 대기 | 대기하지 않음 |
    | 문제점 | 블로킹 발생 가능 | 실행 순서를 이해하기 어려울 수 있음 |
    | 결과 처리 | 바로 반환값 사용 | 콜백, Promise, async/await 사용 |

    | 기능 | 예시 |
    |---|---|
    | 타이머 함수 | `setTimeout`, `setInterval` |
    | Ajax | `XMLHttpRequest`, `Fetch API` |
    | 이벤트 핸들러 | `addEventListener` |

- 비동기 처리를 위해 이벤트 루프와 테스트 큐(이벤트 큐, 콜백 큐라고도 한다)를 사용한다.

    | 개념 | 설명 |
    |---|---|
    | Call Stack | 현재 실행 중인 작업이 쌓이는 공간 |
    | Task Queue | 비동기 함수의 콜백 함수가 잠시 저장되는 큐 영역 |
    | Event Loop | 콜 스택이 비었을 때 태스크 큐의 작업을 콜 스택으로 이동 |
    | Queue | FIFO 방식의 자료구조 |

- `Promise`를 사용하여 비동기 처리와 실패를 명확하게 다룰 수 있다.

    - 생성 : new.Promise(function(resolve, reject) { ... })
        - resolve : 비동기 처리 성공
        - reject : 비동기 처리 실패

    - 상태
        | 상태 | 설명 |
        |---|---|
        | `pending` | 비동기 처리가 완료되기 전, 대기 상태 |
        | `fulfilled` | 비동기 처리가 완료되었고 성공한 상태 |
        | `rejected` | 비동기 처리가 완료되었고 실패한 상태 |

    - 상태 변화
        | 실행 | 상태 변화 |
        |---|---|
        | Promise 생성 직후 | `pending` |
        | `resolve()` 실행 | `pending` → `fulfilled` |
        | `reject()` 실행 | `pending` → `rejected` |

    - 처리
        | 메서드 | 설명 |
        |---|---|
        | `.then()` | 비동기 성공 및 실패 후 처리 |
        | `.catch()` | 비동기 실패 후 처리 |
        | `.finally()` | 성공/실패 여부와 관계없이 이후 처리 |

    - `Promise.all` vs `Promise.allSettled`
        | 구분 | `Promise.all` | `Promise.allSettled` |
        |---|---|---|
        | 실패 시 동작 | 하나라도 실패하면 즉시 전체 reject | 성공/실패와 관계없이 끝까지 기다림 |
        | 반환값 | 성공 값들의 배열 | status 객체들의 배열 |
        | 사용 시점 | 모두 성공해야 의미 있을 때 | 일부 실패를 허용할 때 |
        | 동작 방식 | Fail-Fast | Wait-All |

- async/await은 `Promise`의 계속된 체이닝에 의한 가독성 저하를 해결할 수 있다.
    - await : 비동기 처리가 완료될 때까지 기다린 후, resolve된 값을 반환
    - async : 항상 반환값을 resolve하는 Promise를 반환

- 에러 처리는 `try ... catch`로 할 수 있으며, `try`만 단독 사용하진 못하고, finally를 붙이면 에러 여부와 상관업이 실행되도록 하 ㄹ수 있다.

- 이 파트는 양이 어마무시하게 많다. 대부분 언어의 자유도에서 오는 방식의 차이이고, 이를 더 편리하게 하기 위해 진화해와 지금의 ES6를 구축하게 된 계기가 된 거 같기도 하다.
- 특히 Promise라는 개념이 많이 어색하게 느껴졌으며, 아직 이해보다는 암기에 가까운 것 같다. 마치 양자역학같다.

### 3. React 입문
- Vanilla JS만으로 개발을 한다면, 상태가 바뀔 때마다 개발자가 직접 DOM을 찾아 수정해야 한다.
- 이 과정에서 DOM 추적이 복잡하고, 코드가 길어지고, 실수가 늘어나고, 유지보수가 어려워진다.
- 상태가 바뀔 때마다 DOM을 수정하기보다는, 상태를 만들어 공유하면 어떨까 하는 아이디어로 만들어진 것이 React의 useState이다. 일종의 공유 그릇을 만들어두고 이 상태가 바뀌면 React가 알아서 재렌더링 하는 방식인 셈이다. 이 모습은 변수의 스코프와 닮아있는 듯 하다. 마치 전역 변수 같은 느낌이다.
- React는 상태가 바뀐다고 모든 DOM에 대하여 재렌더링을 하지 않는다. 가상 DOM을 만들어 이전 가상 DOM과 비교해 실제 변경된 부분만 반영한다. 깃허브의 커밋 방식과 비슷해보인다.
- JSX는 문법 확장으로, 별도의 도구를 통해 일반 JS 코드로 변환한다.

- JSX의 핵심 규칙은 다음과 같다.

    | 규칙 | 설명 | 예시 |
    |---|---|---|
    | 최상위 요소는 하나 | 여러 요소를 반환하려면 하나로 감싸야 함 | `<div>...</div>` 또는 `<>...</>` |
    | `class` 대신 `className` | JSX는 JavaScript 문법이므로 `class` 예약어와 충돌 방지 | `<div className="container">` |
    | 닫는 태그 필수 | 일반 태그와 self-closing 태그 모두 닫아야 함 | `<img src="a.jpg" />` |
    | `{}` 안에는 표현식만 | if문, for문 같은 문은 직접 넣을 수 없음 | `{isOpen ? <A /> : <B />}` |

- 컴포넌트는 독립적이고 재사용 가능한 UI 조각으로써, React 앱은 여러 컴포넌트를 조합하여 만들어진다. 이게 가능한 이유는 상태 변화를 알아서 감지해 차이점만 반영해주기 때문에 별도의 하위 요소로의 데이터 갱신 주입이 필요없기 때문이다. 
- 컴포넌트의 이름은 반드시 대문자로 시작해야 하는데, 이는 HTML 태그와 겹치지 않기 위해서이다.

- Props는 부모 컴포넌트가 자식 컴포넌트에게 전달하는 데이터이다. 읽기 전용으로 변수 그릇을 넘겨주는 형태인 셈이다. 그래서 부모 컴포넌트에서 선언된 useState의 변화가 발생해도 자식 컴포넌트에서는 별다른 조치 필요없이 재렌더링된다. 읽기 전용이 포인트이다.
- Props의 특징은 다음과 같다.

    | 특징 | 설명 |
    |---|---|
    | 부모 → 자식 | 데이터는 부모에서 자식 방향으로 전달된다. |
    | 읽기 전용 | 자식은 props를 직접 수정할 수 없다. |
    | 재사용성 향상 | 같은 컴포넌트에 다른 props를 전달해 여러 화면을 만들 수 있다. |
    | 구조 분해 할당 가능 | `{ name, role }`처럼 필요한 값만 바로 꺼내 쓸 수 있다. |

- useState는 변수인데, 자식 컴포넌트에게 쥐어주는 건 배열을 주는 것과 같이 참조의 성격을 띈다.
- 기본 구조는 `const [상태값, 상태변경함수] = useState(초기값);`이며, 예시로는 `const [count, setCount] = useState(0);`가 있다. 상태는 반드시 setter 함수를 통해 변경해야 한다.

- react에서는 불변성을 이유로, 배열 또는 객체를 관리할 때는 새 배열이나 새 객채를 만들어 전달해야 한다. react가 변경을 감지하지 못할 수 있기 때문이다.

- useEffect는 컴포넌트가 화면에 렌더링된 이후에 실행되는 Hook이며, 두 가지 목적을 위해 사용한다.

    | 목적 | 설명 |
    |---|---|
    | 외부 시스템과의 연결 | API 호출, 타이머 설정, 구독 등 React 바깥의 일을 처리 |
    | 실행 타이밍 통제 | 특정 코드가 매번 반복 실행되지 않도록 제어 |

- 컴포넌트는 세 단계의 생명 주기를 가진다.

    | 단계 | 의미 |
    |---|---|
    | Mount | 컴포넌트가 화면에 처음 등장 |
    | Update | state나 props가 바뀌어 다시 렌더링 |
    | Unmount | 컴포넌트가 화면에서 사라짐 |

- useState는 사용자가 버튼을 누르거나 입력할 떄 상태를 바꾸고 화면을 재렌더링 하는데, 실제로는 사용자의 행동이 없어도 코드가 실행되어야 할 떄가 있다. 이를 해결하는 것이 useEffect이다.
- useEffect를 사용하면 생명 주기의 특정 시점에 코드를 실행할 수 있다.

    | 실행 시점 | 예시 |
    |---|---|
    | 처음 화면에 나타났을 때 | API 호출, 초기 데이터 로드 |
    | 특정 state가 바뀌었을 때 | 검색어 변경 시 결과 요청 |
    | 화면에서 사라질 때 | 타이머 제거, 구독 해제 |

- useEffect의 기본 구조는 `useEffect(실행할_함수, [의존성 배열]);`이며, 다음을 의미한다.
    | 구성 | 설명 |
    |---|---|
    | 실행할 함수 | 화면이 그려진 후 실행할 실제 작업 코드 |
    | 의존성 배열 | effect를 언제 다시 실행할지 결정하는 값 목록 |
    | 실행 순서 | 렌더링 → 화면 업데이트 → effect 실행 |

- Cleanup 함수는 effect에서 시작한 작업을 정리하는 함수로, 메모리 누수, 중복 실행, 버그 발생, 성능 저하 등의 문제를 해결할 수 있다.
- Cleanup 함수는 Unmount(컴포넌트가 화면에서 완전히 사라질 때), 다음 Effect 실행 직전에 실행된다.

- 평소 책임 분리를 강력히 추구하는 나에게는 Vanilla JS보다 React가 더 효과적이고 쉬웠다. 근데, 상대적으로 괜찮은거지 사실 아직도 명확히는 모르겠다. 양이 엄청나게 방대해서 힘들다.

### 4. React 구조와 상태 관리

- react에서는 컴포넌트의 단일 책임 원칙(SRP(Single Responsibility Principle))을 만족하도록 설계하여, 각자의 역할만 다하도록 로직을 분리한다.
- 컴포넌트는 너무 작게 쪼개지 않고, 분리할 이유가 있을 때 나누는 것이 좋다.
- 대부분 재사용, 역할 및 책임 분리, 렌더링 최적화, 파일 구조 개선 등의 목적으로 이루어진다.
- 컴포넌트를 분리하면 다음의 규칙으로 폴더 안에 관리한다.

    | 폴더/파일 | 역할 |
    |---|---|
    | `App.jsx` | 앱의 최상위 컴포넌트. 라우터나 전역 Provider 조립 |
    | `main.jsx` | React 앱 시작점. DOM에 앱을 마운트 |
    | `api/` | 서버와의 데이터 통신 담당 |
    | `components/` | 화면을 구성하는 UI 컴포넌트 |
    | `components/common/` | 여러 곳에서 재사용하는 공통 컴포넌트 |
    | `components/chat/` | 특정 도메인 기능 단위 컴포넌트 |
    | `hooks/` | 복잡한 상태 로직을 분리한 Custom Hook |
    | `utils/` | React와 무관한 순수 JavaScript 함수 |
    | `styles/` | 전역 스타일이나 공통 CSS |

- 부모 컴포넌트가 똑같은 특정 컴포넌트 사이의 데이터 공유가 있어야 할 떄가 있는데, 원칙적으로 형제 간 데이터 공유는 불가하다. 부모에서 자식 방향으로만 데이터가 이동해야 하기 때문이다.
- 때문에, Lifting State Up이라고 하는 방법을 쓰는데, 이는 공통 부모가 상태를 소유하는 방식으로 해결한다.

    | 상황 | 해결 |
    |---|---|
    | 두 자식이 같은 state를 봐야 함 | 공통 부모가 state를 가진다. |
    | 한 자식이 상태를 보여줘야 함 | state 값을 props로 내려준다. |
    | 다른 자식이 상태를 바꿔야 함 | 상태 변경 함수를 props로 내려준다. |
    | 형제끼리 직접 통신하고 싶음 | 직접 통신하지 않고 부모를 통해 연결한다. |

- Custom Hook은 `useState`, `useEffect` 같은 React Hook을 사용한 로직을 별도의 함수로 추출한 것이다. 함수 이름은 반드시 `use`로 시작한다.
- Custom Hook을 사용하는 경우는 다음과 같다. 대부분 SRP 만족 또는 로직 분리가 목적이다.

    | 상황 | 설명 |
    |---|---|
    | 상태 로직이 중복될 때 | 여러 컴포넌트에서 같은 API 통신, 로딩, 에러 처리가 반복 |
    | 컴포넌트가 비대해질 때 | JSX보다 데이터 처리 로직이 길어져 가독성이 떨어짐 |
    | UI와 로직을 분리하고 싶을 때 | 컴포넌트는 화면에 집중하고 Hook은 데이터 처리 담당 |
    | React Hook을 포함한 로직을 재사용할 때 | 일반 함수에서는 Hook을 호출할 수 없으므로 Custom Hook으로 분리 |

- Custom Hook의 규칙은 다음과 같다.

    | 규칙 | 설명 |
    |---|---|
    | 이름은 `use`로 시작 | 예: `useProducts`, `useFetch`, `useLocalStorage` |
    | 내부에서 Hook 사용 가능 | `useState`, `useEffect` 등을 호출할 수 있음 |
    | 일반 함수처럼 import 가능 | 필요한 컴포넌트에서 가져와 사용 |
    | 모든 로직을 빼지는 않음 | 복잡하거나 중복되는 관심사만 분리 |

- Tailwind는 복잡한 CSS 방식을 대체하여, 클래스명을 직접 만들어 속성을 부여하는 방식이 아닌, 미리 정의된 작은 스타일 클래스를 조합한다.

- Tailwind의 장점은 다음과 같다.
    | 장점 | 설명 |
    |---|---|
    | 클래스명 고민 불필요 | `.submit-btn`, `.card-wrapper` 같은 이름을 직접 짓지 않아도 된다. |
    | CSS 파일 관리 감소 | 스타일이 JSX 안에 있어 파일 전환이 줄어든다. |
    | 번들 최적화 | 빌드 시 실제 사용된 클래스만 포함해 CSS 크기를 줄인다. |
    | 디자인 시스템 내장 | 색상, 간격, 폰트 크기 등이 일관된 스케일로 제공된다. |
    | 반응형 처리 간편 | `md:`, `lg:` 같은 접두사로 미디어 쿼리 없이 처리 가능 |
    | 상태 처리 간편 | `hover:`, `focus:` 등으로 상태별 스타일 적용 가능 |

- Tailwind의 단점은 다음과 같다.
    | 단점 | 설명 |
    |---|---|
    | `className`이 길어짐 | 스타일이 많을수록 JSX가 길어 보일 수 있다. |
    | 초기 러닝커브 | `p-4`가 `padding: 16px`이라는 식의 매핑을 익혀야 한다. |
    | 복잡한 커스텀 스타일 처리 | 기본 스케일 밖의 세밀한 값은 설정이나 임의값 문법이 필요하다. |
    | JSX 가독성 저하 가능 | 스타일 클래스가 너무 많으면 구조 파악이 어려워질 수 있다. |

- Tailwind에서 자주 쓰는 기본 클래스는 다음과 같다.
    | 분류 | 예시 | 의미 |
    |---|---|---|
    | 배경색 | `bg-white`, `bg-blue-600` | 배경색 지정 |
    | 글자색 | `text-gray-900`, `text-white` | 글자색 지정 |
    | 글자 크기 | `text-sm`, `text-xl`, `text-3xl` | 폰트 크기 지정 |
    | 굵기 | `font-medium`, `font-bold` | 폰트 굵기 지정 |
    | 여백 | `p-4`, `px-6`, `mt-2` | padding, margin 지정 |
    | 테두리 | `border`, `border-gray-200` | 테두리 지정 |
    | 둥근 모서리 | `rounded`, `rounded-lg`, `rounded-xl` | border-radius 지정 |
    | 그림자 | `shadow-sm`, `shadow` | box-shadow 지정 |
    | 레이아웃 | `flex`, `grid` | 레이아웃 방식 지정 |

- Tailwind에서의 반응형 접두사 기준은 다음과 같다.
    | 접두사 | 최소 너비 | 대상 기기 |
    |---|---|---|
    | 없음 | 0px 이상 | 모든 크기, 기본값 |
    | `sm:` | 640px 이상 | 작은 태블릿 |
    | `md:` | 768px 이상 | 태블릿 |
    | `lg:` | 1024px 이상 | 데스크톱 |
    | `xl:` | 1280px 이상 | 큰 데스크톱 |

- Tailwind에서의 Flexbox 개념은 다음과 같다.
    | 개념 | 설명 |
    |---|---|
    | Container | 정렬할 요소들을 감싸는 부모 태그 |
    | Item | 컨테이너 안에 나열되는 자식 태그 |
    | Main Axis | 요소들이 배치되는 주축 |
    | Cross Axis | 주축에 수직인 교차축 |

- 이번 파트도 양이 엄청나게 많다. 이걸 전부 다 외울 수는 없을 거 같아, JS와 React 부분은 AI의 힘을 빌려 학습일지에서 간단하게 찾아볼 수 있도록 정리해보았다. 좋은 선택이었던 것 같다.

### 5. Github 협업
- 컴퓨터공학을 전공하거나 개발에 관심이 있어 다른 사람들과 협업을 한다면 Github는 필수로 사용하는 추세다. 그만큼 원격 협업 플랫폼에서 강력한 지위에 위치해 있다.

- Git workflow는 다음의 주요 브랜치로 이루어져 있다.
    | 브랜치 이름 | 설명 |
    |---|---|
    | `main` 또는 `master` | 제품 출시 버전을 관리하는 브랜치 |
    | `develop` | 다음 출시 버전을 개발하는 브랜치 |
    | `feature` | 새로운 기능을 개발할 때 사용하는 브랜치 |
    | `release` | 다음 출시 버전을 준비하는 브랜치 |
    | `hotfix` | 긴급한 버그 수정이 필요할 때 사용하는 브랜치 |

- 흐름은 다음과 같다.
    | 단계 | 브랜치 | 핵심 역할 | 흐름 |
    |---|---|---|---|
    | 1 | `develop` | 개발 최신 코드 시작 | 개발 기준 브랜치 |
    | 2 | `feature` | 기능 개발 | `develop` → `feature` |
    | 3 | `feature` 병합 | 기능 완료 | `feature` → `develop` |
    | 4 | `release` | 릴리즈 준비 | `develop` → `release` |
    | 5 | `release` 병합 | 안정화 | `release` → `develop` |
    | 6 | `main` | 배포 | `develop` → `main` |
    | 7 | `main` | 안정 코드 | 배포 버전 유지 |
    | 8 | `hotfix` | 긴급 수정 | `main` → `hotfix` → `main` |

- Branch를 통해서 같은 프로젝트 내에서 각자의 작업을 분리하여 진행할 수 있는데, 브랜치 유형이 중요하다. 유형의 종류는 다음과 같다.
    | 유형 | 접두사 | 설명 |
    |---|---|---|
    | 기능 개발 | `feature/` | 새로운 기능 개발 |
    | 버그 수정 | `bugfix/` | 일반 버그 수정 |
    | 긴급 수정 | `hotfix/` | 프로덕션 환경 긴급 버그 또는 보안 수정 |
    | 릴리즈 준비 | `release/` | 릴리즈 버전 준비 및 QA |
    | 실험 / 테스트 | `experiment/` | 실험적 기능 개발 |
    | 문서 작업 | `docs/` | 문서 수정 및 추가 |

- Collaborator는 초대된 팀원을 의미하며, 초대되면 Commit, Push 등이 가능하다.
- COllaborator와 함께 개발에 진행하고 Branch를 합치는 Merge 과정을 겪게 되는데, 아무리 독립적으로 개발을 할 수 있다해도 충돌은 피할 수 없다. 이를 Conflict라고 하며, 이를 해결해야 Merge를 할 수 있다.
- 원활한 Merge를 위해서 원천 Branch에 수정사항이 생기면 즉각적으로 Pull을 받고, PR 요청 시에는 해당 Branch에 대한 정보를 상세히 기록하는 것이 매너이다.

- FOrk는 내용이 동일한 Repository를 내 계정으로 복사하는 것으로, Fork한 Repository를 수정해도 원래 Repository에는 바로 반영되지 않는다. 반영하려면 PR을 생성해야 한다.

- 그 외 기능들은 대부분 알고 사용해본 적이 있어 쉽게 이해할 수 있었다.

- 시도: 워낙 내용이 방대해서, 결국 강의 교안을 ChatGPT에게 정리하여 md 형식으로 제공해달라고 했다. 
- 해결: 강의 자료와 실습으로는 이해하기 비교적 어려웠던 부분을 그나마 이해할 수 있었다.
- 배운 점: 내용이 방대하다면, 그 내용에 대해 단순히 쥐고만 있기보다는, AI에게 정리를 맡기는 것도 하나의 해결 방법인 듯 하다. 다만, AI를 사용하면서 그 정보가 정확한 지는 2차 검증이 필요하다.

## 🔁 이번 주 회고 (KPT)
- Keep: 강의 내용의 정리가 어렵다면 AI의 힘을 1차로 빌리고 정리본을 읽고 내용에 대해 2차 검증하며 자신의 방법으로 재정리하기.

- Try: 너무나 방대한 양을 그때마다 정리하되, 정말 막막할 정도의 양과 더불어 강의 내용과 실습으로 이해가 되지 않은 부분에 대해서 AI에게 물어보며 추가 조사하여 자신의 방법으로 재정리하기.
