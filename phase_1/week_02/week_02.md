### 1. 구조화된 요청은 무어냐?
- LLM은 기본적으로 **자연어**를 출력한다.
- 예를 들어보자.
    - 1주차에 만든 LLM이 사용할 수 있는 Tool을 사용하도록, `"내일 오후 2시에 철수랑 영희와 영화 일정을 잡아줘"`라고 부탁을 해보자.
    - LLM은 만들어둔 `personal_create_schedule` 도구를 사용하여 인-메모리에 일정을 저장하고 `"내일 오후 2시에 철수랑 영희와 영화 일정을 잡았습니다."`를 출력할 것이다.
- 이러한 비서 Tool을 사용하는 서비스로 만들어보자고 생각해보자. 어떤 문제가 발생할까?
    - 만약 개인 비서 서비스를 만들었고, LLM이 예약한 일정을 자연어가 아닌 별도의 UI로 보여주려고 한다면 LLM이 뱉은 자연어를 파싱해야할 일이 생길 수 있다.
    - 근데 LLM은 태생이 **확률**이다. 특정 데이터를 가지고 다음 글자(토큰)를 확률을 통해서 생성하게 되며, 이로 인해서 자신이 어떤 프롬프트와 어떤 데이터를 줬는지에 따라 그 차이가 명확하게 나뉜다.
    - 자연어 답변이 LLM이 답변을 할 때마다 다르면 파싱하기 위한 식을 규정할 수 없다.
    - 다르게 말하면, **기본적인 LLM의 모든 답변에 대해 완벽한 파싱을 수행할 수 없다!**
- 파싱이 안된다고? **구조화된 출력**(Structured outputs)이라면 가능하다!
    - 아까부터 LLM은 태생이 확률이고, 요청 때마다 답변이 다르다고 했다.
    - 사람들은 생각했다. **Framework에서 구조화된 출력을 하도록 검사를 진행하게 만든다면?**
    - LLM이 구조화된 출력을 하도록 계속해서 반복하도록 말이다!
    - 예를 들어보자.
        - { name: str, time: datetime, location: str }의 구조화된 출력 양식이 있다고 해보자.
        - 이 구조를 별도의 Framework인 Pydantic Model을 사용해서 규정해보자.
        - LLM은 자신의 답변을 만들고 해당 Model에 담아봤는데 누락되거나 이상한 값이 담기게 되면 Framework에서 데이터 검사를 진행할 때 **니 데이터 이상해!**라고 알려주게 된다.
        - 오류를 발생시키면 LLM이 해당 구조를 만족할 때 까지 반복할 것이고, 통과되면 그렇게 데이터가 만들어지게 될 것이다.
    - 결국, 우리가 Framework로 Server를 만들고 데이터 입출력을 검증할 때 사용하는 Framework 내지 Library를 LLM의 답변을 검증하는데 사용하면서 구조화된 출력을 만들어내게 된다.
- 구조화된 출력이 뭔지는 알았다. 그러면 예시를 들자면?
    - 많이들 사용하는 것으로 JSON과 Pydantic이 있다.
    - JSON
        - 예시 : { name: "철수", time: "09:00", location: "학교" }
        - 장점 : 간단한 프롬프트, JSON 형식으로 쉽게 변환할 수 있다.
        - 단점 : key가 누락될 수 있다 (구조 붕괴) -> 파싱 등 데이터 가공 및 CRUD에서 잠재적 오류 발생의 여지가 있다.
    - Pydantic class
        - 장점 : key 누락을 방지할 수 있다 (구조를 충족하지 않으면 오류 반환)
        - 단점 : 파싱 단계가 길고, 특히 JSON을 파싱하는 과정에서 오류가 많이 발생한다.
- 포인트는 **파싱하기 좋게 LLM이 답변을 뱉도록 만든다**는 것이다!
- 2주차의 목표는 구조화된 요청으로만 만드는 것이고, 이 구조화된 데이터를 저장하거나 하진 않는다. 그건 다음 주차에 진행한다.

### 2. 답변을 더욱 명확하게! 프롬프트 엔지니어링!

#### 1. Shot? 이게 뭐야?
- 어원: 찰칵!
    - **Shot**의 근본적 어원은 카메라의 **촬영**(Snapshot, Mugshot 등)에서 왔다.
    - 마치 누르면 총알이 나가는 것처럼, 카메라도 버튼을 누르면 Flash가 터지면서 찰칵 찍히기 때문이다.
- 의미의 변화: 한 장만 보여준다!
    - **Shot**의 의미가 변화하면서, AI 학습 분야에서 쓰이기 시작했다.
    - **One-Shot Learning**이라 하면, AI에게 특정인의 사진을 딱 한장(One shot)만 보여준다는 의미로 사용했다.
    - 즉, **Shot**은 **이미지 한 장**을 의미하게 된 것이다.
- 의미의 확장: 학습 데이터!
    - 시간이 지나면서 AI 기술이 이미지뿐만 아니라 텍스트(자연어 처리) 분야로도 확장됐다.
    - 이 과정에서 **Shot**이라는 단어는 **AI에게 주어지는 학습 데이터 1개** 또는 **예시 1개**를 통칭하는 고유 명사처럼 그 의미가 확장됐다.
    - 그 학습 데이터(예시)를 몇 개 보여줄 건지에 대해 접두사가 달라지게 된다.
        - **One-shot**: 예시를 1개만 보여준다.
        - **Few-shot**: 예시를 몇 개(보통 2~5개)를 보여준다.
        - **Zero-shot**: 예시를 아예 보여주지 않는다.
- AI 패러다임의 변화! 즉각적인 반영!
    - LLM이 등장하면서, 모델의 추가적인 학습을 통해 직접 뜯어고치는 방식이 아닌, 대화창(프롬프트)와 에시를 몇 개 같이 제공하는 것만으로도 AI가 그 자리에서 패턴을 파악하고 학습한 것과 똑같은 효과를 내기 시작했다.
    - 즉, **학습(Learning)**보다는 **프롬프트 예시**가 중요해진 셈이다.
    - 그래서 프롬프트로 예시를 입력하는 의미를 강조하여 [**One-shot**/**Few-shot**/ **Zero-shot**] Prompt라고도 한다.

#### 2. 프롬프트 엔지니어링으로는 뭐가 있어?
- 예시: **Shot**
    - Zero-shot Prompting
        - AI에게 아무런 예시나 힌트를 주지 않고 곧바로 질문이나 지시를 던지는 방식
        - 예시: "사과를 프랑스어로 번역해줘"
        - 일반적인 지식, 단순 번역, 일상적인 대화 등 예시 없이도 AI가 충분히 잘 해낼 수 잇는 쉬운 작업에 사용
    - Few-shot Prompting
        - 질문 전에, AI가 어떤 패턴이나 형식으로 대답해야 할 지 감을 잡을 수 있도록 몇가지 예시(Input/Output 쌍)을 먼저 제공하는 방식
        - 예시: "한국어:안녕 -> 영어:Hello, 한국어:강아지 -> 영어:Dog"
        - 답변의 특정 포멧(JSON, 표 형태 등)을 맞춰야 하거나, AI가 문맥이나 톤을 예시를 보고 똑같이 따라하게 만들고 싶을 때 사용
- 예시: **Instruction**
    - AI에게 단순한 질문을 넘어, 역할, 말투, 형식, 제약 조건 등을 아주 구체적이고 명확하게 지시(명령)하는 방식
    - 예시: "너는 10년 차 파이썬 개발자야. 내가 짠 코드를 보고, 메모리 효율성을 개선할 수 있는 피드백을 줘. 햇병아리 대학생 1학년도 이해할 수 있도록 쉽게 작성하고, 반드시 3줄 이내로 요약해서 답변해줘"
    - 답변의 퀄리티를 통제하고 싶을 때 사용
- 예시: Chain of Thought (**CoT**, 생각의 사슬)
    - AI에게 즉각적인 정답을 바라는 게 아니라, 논리적인 풀이 과정을 거치도록 만드는 방식. 포인트는 "차근차근 단계별로 생각해보자(Let's think step by step)"!
    - 예시: "철수에게 사과가 5개가 있었어. 영희가 2개를 뺏어갔고, 엄마가 3개를 새로 사주셨어. 철수에게 남은 사과는 몇 개야? 정답을 말하기 전에 차근차근 단계별로 계산 과정을 설명해줘"
    - 복잡한 추론이 필요한 상황에서 사용. 수학 계산, 복잡한 논리 퀴즈, 알고리즘 문제 등이 해당.

### 3. 메인 과제: Nana야! 내가 정해준대로 답해봐!
- 이번 Week 2의 목표는 AI(LLM)이 만들어둔 규격(Pydantic)대로 답변하도록 하는 것이다.
- `StructuredRequest` 구현
    - LLM이 하나의 일정마다 어떤 규격으로 답변해야 할 지를 규정하는 중요한 부분이다.
    - `kind`는 요청 종류를 의미한다. 개인적인 일정일 수 있고, 단체 일정일 수도 있고, 단순한 Todo나 Reminder일 수 있다. 그런 종류를 카테고리화하는 것이다.
    - 그 에는 일정 제목, 날짜, 시작 시간, 종료 시간, 단체 일정이라면 멤버 목록, 일정의 우선순위, 일정의 이유, 일정 잡기 프롬프트 원문이 묶이게 된다.
- `StructuredRequestBatch` 구현
    - 우리가 비서에게 요청하는 일정 관련 부탁은 한 문장에 여러개가 될 수 있다.
    - 예를 들면, "철수와 영희랑 내일 오후 2시에 영화보기, 길동이랑 현우랑은 모레 오전 10시에 헬스장에서 운동하기 일정을 잡아줘"라고 하면 일정이 2개가 있어야 한다.
    - 이 상태에서 앞서 규정한 `StructuredRequest` 스키마의 경우에는 하나의 일정만을 다룰 수 있다.
    - 일정이 여러 개면 각각 하나의 독립적인 일정으로 분리하여 `StructuredRequest`로 만들고 이를 리스트로 담아 뱉도록 설계하기 위해 `StructuredRequestBatch` 스키마를 만든다.
    - 다만, 한 문장에 하나의 일정만 있더라도 `StructuredRequestBatch`인 리스트를 기준으로 기능을 만들어야 하기 때문에 이러한 조건을 LLM이 명심할 수 있도록 프롬프트나 해당 스키마의 설명으로 제공해야 한다.
- `week02_system_prompt`, `week02_prompt_parts`
    - 우리가 원하는 구조화된 출력을 하도록 명령하는 부분을 담당한다.
    - 특히, "최종 답변은 예외없이 StructuredRequestBatch 구조로만 생성한다"가 해당 과제의 핵심이다.
    - 날짜와 시간 계산에 환각(할루시네이션)이 없도록 요청자의 날짜와 시간을 프롬프트로 제공하고, 구조화된 출력을 위한 조건들을 같이 기입해준다.
    - 이를 통해 자연어로 답하는 일이 거의 없고, 가끔 분류를 잘못한다거나 값을 이상하게 넣기는 하지만 대부분의 경우에서 잘 작동하는 모습을 보인다.

### 4. 심화 과제: 불확실성을 방어해보자!
- LangChain은 원문(LLM의 응답)을 처리한 결과가 사용하는 LLM 모델(OpenAI, Claude, Gemini, etc)이나 LangChain 패키지 버전에 따라 Pydantic 객체로 완벽하게 나오기도 하고, 파이썬 기본 딕셔너리(dict)로 나오기도 한다.
- 이런 상황에서 만약 우리가 예상치 못한 자료형이 나오게 된다면, 파싱에서 문제가 생길 것이다.
- 심화 과제는 이런 응답을 처리하는 과정의 불확실성을 방어하도록 하는 것이다!
- `_coerce_structured_reuqest 구현`
    - LangChain의 구조화된 출력 결과를 우리가 규정한 `StructuredRequest`로 만드는 부분이다.
    - 이미 `StructuredRequest`인지에 대해서 **Early Return**하고, `딕셔너리(dict)`라면 `StructuredRequest` 구조를 사용할 수 있는지 `model_validate` 함수를 통해 검증한다.
        - `model_validate`는 모델에 정의된 타입과 일치하는 지 확인함과 동시에, 가능한 경우에 자동 형변환까지 수행해서 조건을 만족한다면 형변환을 해준다.
    - `StrcutredRequest`가 아니고, StructuredRequest를 만족하지 않는 딕셔너리(dict)이거나 그 외에 다른 데이터 형식이라면 RuntimeError를 발생시켜 LLM 응답을 조용히 통과시키지 않는다.
- `extract_structured_request 구현`
    - 앞서 일반적인 LLM은 자연어를 기본 답변하고, 해당 답변을 코드 측면에서 사용하려면 구조화된 데이터가 필요하다고 했다.
    - `with_structured_output` 함수를 통해 LLM에게 **"이상한 소리하지 말고, 내가 준 양식(설문지)에 맞춰서만 답안을 제출하렴!"** 라고 강제하는 과정이다.
        - `StructuredRequest`를 LLM이 이해할 수 있도록 `JSON Schema 형태로 번역
        - `method="function_calling"`을 통해 **"너(LLM)는 텍스트를 쓸 게 아니라, 이 스키마에 맞는 함수를 실행하기 위한 인자(Arguments)를 생성해야 해"**라고 모델의 생각 구조를 세팅
        - 설정이 끝난 LLM 객체(`structured_llm`)을 반환
    - `invoke` 함수를 통해 세팅을 해둔 LLM에게 **실제로 실행하도록 명령**하는 역할을 한다.
        - `invoke` 안 메시지 리스트를 HTTP Request 규격으로 포장
        - LLM 제공자의 서버로 실제 API 요청
        - LLM 서버에서 JSON 텍스트 응답이 오면, `invoke`가 내부적으로 `json.loads()`를 시래아고 이를 Pydantic 객체 또는 딕셔너리로 자동 파싱한 뒤에 최종 결과물로 제공
    - 그렇게 받은 최종 결과가 아직은 `StructuredRequest`인지, `JSON`인지, `딕셔너리(dict)`인지 모르기 때문에 앞서 구현한 `_coerce_structured_request`로 정규화한다.
- `extract_schedule_request 구현`
    - 앞서 규현한 `_coerce_structured_request`와 `extract_structured_request`를 통해 최종적으로 복잡한 자연어를 깔끔한 Pydantic 객체로 바꾸는 역할을 한다.
    - `@tool` annotation을 붙여 LLM이 사용할 수 있는 tool 형태로 제공해서, LLM이 해당 Tool을 적절하게 사용하도록 유도하는 셈이다.
    - 즉, 사용자의 요청을 LLM이 이 도구를 사용해서 Pydantic 객체로 만드는 셈인 것이다.

    - 최신화가 되지 않은 파일들이 발생하여 파일 추적이 꼬였다는 것을 파악
- 시도
    - `chagyeongho/week2` 브랜치 삭제
    - `main` -> `chagyeongho/final`로 merge 재시도했으나, merge 할 commit이 없다고 나옴
    - 결국 `Claude Code`에게 상황 파악을 지시하고 개선하기 위한 솔루션을 처방받던 중 최신화 공지사항이 올라와 구현했던 메인 과제는 수동 백업을 진행하고 가이드대로 진행하여 갱신
- 해결
    - `run.sh`을 제외한 나머지 코드들은 모두 최신화 완료하고, sh 파일은 수동 갱신
- 배운 점과 아쉬운 점
    - 웬만하면 Github 통제권을 AI에게 맡기고 싶지 않았으나, Git 사용법을 간단한 commit, push, pull, fetch 등만 알고 있고 별도의 flag 기능들은 잘 몰라 어쩔 수 없이 맡길 수 밖에 없었음
    - 최신화 계획을 Claude에게 설명받아 수동으로 진행할 수 있는 건 최대한 직접 진행하였고, 모르는 부분은 명령어를 보고 승인 여부를 판단함
    - Git 명령어를 더욱 숙지해야겠다는 생각이 듦

### 문제 2: Nana가 구조화된 출력이 아닌 자연어로 답변하는 현상 발생
- 상황
    - 공지사항을 통한 week2 과제 내용 최신화를 진행하기 전인 `week02_structure_natural_language_requests.py`의 메인 과제 부분을 구현한 후 발생한 문제
    - LLM의 답변이 구조화된 출력이 아닌 week01과 같은 자연어로 답변함을 파악
- 시도
    - 2주차 과제 최신화 공지사항이 올라오기 전에 프롬프트 문제라고 인식하여 프롬프트에서 구조화된 출력을 하라는 강력한 지시를 넣었으나 여전히 자연어로 답함.
    - 코드적인 부분에서 틀린 부분이 있는지를 파악하기 위해 Claude에게 테스트 케이스를 제작하고 테스트할 것을 명령함
    - 여러 테스트 케이스에서 여전히 자연어로 대답하는 경향을 보여 `student_parts` 외 다른 디렉터리의 파일들을 수정해볼 것을 권고했으나, 교육생은 다른 부분을 건들면 안되므로 거절함.
    - 이후 최신화 공지사항이 올라와 구현해뒀던 week02 파일을 수동 백업하고 다시 브랜치를 생성하고 백업한 파일을 넣어 테스트를 진행함.
- 해결
    - LLM의 대답이 자연어가 아닌 구조화된 출력이 됐음
    - 다만, week02 과제 파일에서 주석이 최신화가 이루어지지 않아서 심화 과제가 없다는 것을 1차 PR 후에 알게 되어 서둘러 멘토님의 피드백을 받은 후 week02 파일의 최신화 및 심화 과제 구현을 마침
- 배운 점과 아쉬운 점
    - 이번 주차의 과제는 과제의 최신화 문제가 가장 컸던 걸로 보인다.
    - 사실 1차 PR만에 승인이 되고 추가적으로 구현해보고 싶은 기능들을 구현해보고 싶었으나 그러지 못했다.
    - 과제를 너무 서둘러 하려고 했던 점이 좋지 않게 작용했다. 다음주부터는 과제를 너무 빠르게 하려고 하지 않고 꼼꼼히 하려고 노력해야겠다.
