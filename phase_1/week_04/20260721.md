### RAG(Retrieval Augmented Generation) 초기형
- 왜 필요한가?
    - LLM은 성능이 부족하다 : 모델이 커서 최신 데이터 학습 시간 및 비용이 많이 들어감 -> 학습 시키기 힘듦
    - 학습시킬 데이터를 학습시키기보다 **참고**할 수 있도록?
    - 프롬프트를 청크(chunk) 단위로 나누고 이를 적절히 참고하기 위해 RAG 필요!
- 데이터 검색, 프롬프트 증강, 답변!
    - LLM Embedding
        - Text2Vec 후 Vector DB에 저장!
            - Embedding 모델이 학습이 잘 돼 있어야 유용하게 쓸 수 있음
            - 즉, Embedding도 모델이라서 가중치를 사용해서 값을 Vector로 바꿀 뿐임!
            - **차원(Dimension)**은 **특성(특징)**의 개수!
            - Vector DB는 Text:Vector 쌍을 index로 보관하고 있다고 생각하면 됨
        - Embedding Vector는 정보(특징)를 내제하고 있음 (관계 내제)
        - 원래는 한 글자를 한 Token으로 취급하지만, 여기서는 문장을 토큰(Token)들의 평균(Mean pool)으로 처리?
            - 특정 문장을 한 글자씩 임베딩하고 문장을 그 글자들의 임베딩 값의 평균으로 처리함?
            - 청크(Chunk) 단위로 자르기도 하는데 그 단위는 다양함
    - Retrieval(검색하다)
        - 질문 프롬프트도 Embedding하고, 저장해뒀던 Embedding Vector들과의 거리(distance)를 기반으로 검색해서 연관있는 정보를 선출하여 연산에 참고함
        - 거리가 짧을수록 연관있는 정보로 이를 프롬프트로 참고!
    - Augmented (Prompt Synthesis)
        - 질문 프롬프트를 검색해서 선출한 정보를 덧붙여 증강(강화)해서 LLM에게 지시
- 약점
    - Input Token의 증가 -> Prompt Caching 등장!
    - 비효율적임
- 현대에는 Retrieval과 Augmented 부분을 Tool로 만들어 유연하게 사용!
