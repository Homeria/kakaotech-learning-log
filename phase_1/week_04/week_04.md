## 📚 이번 주 학습한 것

### 1. 이론 — 나나야, 이번엔 "기억을 찾아오는" 능력이야 (RAG)

#### 1) RAG란 무어냐?
- LLM은 **학습 시점에 고정된 지식**만 가지고 있다. 내가 어제 적어둔 메모, 지난주에 저장한 일정, 예전에 나눈 대화 같은 **개인 데이터**는 애초에 모른다.
- 모르는 걸 물어보면 혼나기 싫어서 일정을 **그럴듯하게 지어낸다**(환각). 없는 일정을 지어내면... 심각한 사안이다.
- 그래서 나온 게 **RAG(Retrieval-Augmented Generation)**다. 이름을 그대로 풀면 "검색(Retrieval)해서 → 관련 자료를 프롬프트에 끼워넣어(Augmented) → 그걸 근거로 답(Generation)"이다.
- 비유하자면, **시험 보기 전에 관련 페이지를 펼쳐놓고 오픈북으로 답하게 하는 것**이다. 나나가 기억에만 의존하지 않고, "일단 자료를 찾아본 다음" 그 결과로만 답하도록 만드는 셈이다.

#### 2) 핵심 — RAG를 "만능 함수 하나"로 보지 말자
- 오픈북이라면, "하나의 책에 모든 데이터를 다 저장하고 검색 도구 하나 만들어서 쓰게 하면 되지 않을까?" 싶다. 근데 나나가 기억할 게 한 종류가 아니다. **출처가 다르다.**
    - **개인 참고자료** : 내가 적어둔 규칙·선호·메모 ("회의실은 최대 2시간", "점심시간엔 회의 X")
    - **저장된 일정/할 일/알림** : 지난 주차에 SQLite에 영속화한 구조화 기록
    - **과거 대화 발화** : 저장까지는 안 했지만 예전에 나눈 잡담성 대화 ("저번에 제주도 여행 얘기했던 거")
- 그리고 이 출처들은 **저장 방식도 검색 방식도 다르다.** 참고자료·대화는 의미로 찾는 **벡터 검색**(ChromaDB), 저장기록은 키워드로 찾는 **LIKE 검색**(SQLite).
- 그래서 이번 주의 포인트는 **"만능 검색기 하나"가 아니라 "출처별 검색 도구를 따로 두는 것"**, 그리고 **질문 성격에 맞는 도구를 나나(LLM)가 직접 고르게** 하는 것이다.
- 즉 나나에게 **서랍이 여러 개**인 셈이다. "이건 규칙 서랍, 저건 일정 서랍, 그건 대화 서랍." 어느 서랍을 열지 나나가 판단하게 만드는 게 목표다. (이번 주 제목이 "그 도구 아니야 내려놔.."인 이유... 나나가 서랍을 자꾸 잘못 연다.)

#### 3) 벡터 검색 & 임베딩 (의미로 찾는다)
- 키워드 검색("점심" 글자 든 것 찾기)은 표현이 조금만 달라도 못 찾는다. "점심때 회의 잡아도 돼?"에 "점심 시간 보호" 규칙이 걸리려면 의미로 이어져야 한다.
- 그래서 **임베딩(embedding)**을 쓴다. 문장을 **숫자 벡터**로 바꾸는 것인데, 의미가 비슷하면 벡터 공간에서 **가까이** 있다.
- 검색은 "질문 벡터와 가까운 문서 벡터"를 찾는 것이고, 가까움의 척도가 **distance**다. **distance가 작을수록 유사**하다. (헷갈리기 쉬운데 "가깝다=작다=유사". 나도 처음에 주석을 "distance 높을수록 유사"라고 거꾸로 적었다가 고쳤다. 거리니까 작을수록 가까운 게 맞다!)
- 이 벡터를 저장·검색해주는 게 **ChromaDB**(벡터 DB)이고, 임베딩은 OpenAI 임베딩 모델로 만든다.

#### 4) Agentic RAG — "검색할지 말지"도 나나가 정한다
- RAG에도 결이 두 개다. **고전 RAG**는 모든 질문에 무조건 검색→생성(검색 강제). **Agentic RAG**는 검색이 **도구**라, 나나가 필요하다 싶을 때만 부른다(검색 여부·출처가 나나의 판단).
- 이 앱은 **후자**다. 매 턴 자동이 아니라 질문에 따라 **조건부**로 검색한다. (이 성질이 뒤에서 라우팅 문제로 이어진다.)
- 헷갈렸던 것: "직전 대화는 매번 참고 안 하나?" → 아니다. **현재 대화 히스토리는 항상 context로 들어간다**(agent_runtime이 넘겨줌). 도구 검색은 그것과 **별개로** 저장소(다른 대화 포함)를 의미검색하는 것이다.


### 2. 메인 과제 (1차): 참고자료·저장기록 서랍 만들기
- 이론을 과제로 옮긴다. 1차는 **참고자료(추가·검색)**와 **저장기록(검색)** 도구를 만든다.
- 구현 흐름은 3주차에서 배운 그 패턴 그대로다. **`@tool(args_schema=...)`로 검증된 인자를 받아 → helper가 store 결과를 정리 → `json_payload`로 JSON 문자열 반환.** 도구는 얇은 입구, 실제 검색은 store가 한다.
- `add_personal_reference` 구현
    - 참고자료를 ChromaDB(`REFERENCE_STORE`)에 저장하는 도구.
    - helper(`add_personal_reference_dict`)에 위임하고 `{reference_backend, reference}`를 반환한다. 이론 2의 "규칙 서랍에 새로 적어두기"에 해당.
- `search_personal_references` 구현
    - 참고자료 **벡터 검색**.
    - top-level `{"hits": [...]}`(id/content/distance/metadata)를 반환해서, 나나가 근거 문서를 바로 읽을 수 있게 한다. (distance가 작을수록 둘이 유사)
- `search_saved_requests` 구현
    - SQLite 저장 요청을 **LIKE 키워드 검색**.
    - top-level `{"rows": [...]}`를 반환. 같은 '검색'이어도 참고자료(벡터)와 **store도 검색 방식도 다르다**는 게 여기서 코드로 드러난다.
- helper(`search_personal_reference_hits`, `search_saved_request_rows`)가 store 결과를 도구가 쓰기 좋은 모양으로 정리한다.


### 3. 심화 과제 (2차): 과거 대화 RAG + 통합 검색 + 라우팅 프롬프트
- 2차는 세 번째 서랍인 **과거 대화**를 열고, 나나가 세 서랍 중 맞는 걸 고르게 프롬프트까지 붙인다.
- `search_conversation_messages` 구현
    - 여기서 이론에 없던 실전 문제 두 개를 실제로 풀어야 했다.
    - **(1) lazy sync**
        - 대화 원본은 SQLite, 검색은 ChromaDB(색인).
        - ChromaDB는 SQLite의 **파생 캐시**라, 검색 전에 `sync_from_sqlite`로 바뀐 걸 반영한다.
        - 근데 **lazy**하게 = **온디맨드**(검색 필요할 때만) + **증분**(`source_hash`로 안 바뀐 대화는 skip).
        - **임베딩은 API 호출(비용·시간)**이라 전체를 매번 다시 만들면 낭비. "필요할 때, 바뀐 것만"이 lazy의 핵심.
    - **(2) 현재 대화 제외**
        - sync가 방금 내가 친 말까지 색인에 넣어서, "과거 대화 찾아줘"에 방금 한 말이 과거인 척 나온다. 그래서 현재 대화 하나를 뺀다.
        - 현재 대화 id는 `current_session_scope()`로 얻는다(실제 세션이면 대화 id, 세션 밖이면 기본값).
    - 반환은 `{hits, rows, context, rag_backend, sync}`.
- `search_nana_memory` 구현
    - 이전 버전 호환용 **통합 검색**(참고자료 hit + SQLite 일정 chunk를 한 context로 묶음).
    - 새 구현의 핵심은 출처별 tool이지만, 기존 trace 호환을 위해 남겨둔다.
- `week04_prompt_parts` / `build_week04_agent`
    - 세 출처 중 맞는 도구를 고르게 지시하는 프롬프트 + Week 1~4 누적 agent.
    - **도구를 만들어 줬다고 나나가 알아서 잘 고르는 게 아니다.**
    - 그래서 시스템 프롬프트에 "규칙/선호면 참고자료, 저장 일정이면 저장기록, 예전 대화면 대화검색" 같은 **출처 선택 기준**을 CoT로 명시하고, **도구 docstring**에도 트리거 문구를 심는다(LangChain이 docstring을 도구 설명으로 LLM에 넘기므로).


### 4. 테스트: 나나가 서랍 잘못 여는 걸 "숫자로" 잡다
- 도구·프롬프트를 다 만들고 물어봤더니 나나가 서랍을 자꾸 잘못 연다. 근데 **감으로 프롬프트를 고치면 뭐가 나아졌는지 모른다.** 그래서 3주차처럼 **측정할 테스트부터** 만들었다.
- **지표를 둘로 분리** : ① 라우팅(도구 선택) 정확도 ② 답변 정확도. (도구는 맞게 골랐는데 답이 틀린 경우와, 도구부터 틀린 경우는 완전 다른 문제니까.)

#### 1) 1차 테스트
- **테스트 설계** : 6개 카테고리 × 5단계 난이도, **총 50케이스**. 실제 `data/`를 오염 안 시키게 **격리된 DB/ChromaDB에 시드**해서 측정(케이스별 2회 + 판정 갈리면 타이브레이크).
- **개선 전 결과 → 이슈 발견** : 라우팅 54%. 주요 이슈 3종 —
    - "기억해줘/메모해줘"를 참고자료 추가가 아니라 **일정 저장으로 오라우팅**(게다가 "기억했다"고 답해 겉보기엔 정상).
    - 신호어 약한 대화 질문이 **대화검색 대신 저장기록**으로 샘.
    - 참고자료를 **안 찾고 되묻기**.

#### 2) 1차 테스트 분석 및 개선하여 2차 테스트
- **개선**
    - 프롬프트를 4블록으로 재구성
        - ① 되묻지 말고 도구로 먼저 검색
        - ② 출처 선택 기준 + 검색어는 짧은 핵심 명사
        - ③ 참고자료 '추가' vs 일정 '저장' 구분
        - ④ 빈 결과 시 다른 출처(특히 대화)로 폴백
    - 그 외: 도구 docstring에 트리거 문구 심기, `search_saved_requests` 토큰 재검색 추가
- **결과 : 라우팅 54% → 90%, 답변 64% → 89%.** "기억해줘" 오라우팅은 14% → 86%.

#### 3) 과적합 테스트
- **진짜 개선인지 검증 (held-out 과적합 테스트)**
    - 50케이스로 튜닝했으니 그 50개에 과적합됐을 수 있다. 그래서 **튜닝에 안 쓴 새 25케이스**(새 시드 + 프롬프트에 없는 표현)로 재측정을 하였다.
    - 라우팅 **88%**(−2pp). 큰 하락이 없어 과적합의 뚜렷한 징후는 없었다. (단, 25개는 표본이 작아 "확정"은 아니고 "징후 없음"까지.)
- **배운 점** : 감이 아니라 **숫자로 개선을 증명**하는 습관. 그리고 in-sample(튜닝 데이터) 점수는 과대평가라 **out-of-sample(안 본 데이터)로 재봐야** 진짜 실력이라는 것.


## 🧱 막혔던 지점 & 해결 과정

### current_session_scope() 기본값
- 상황
    - `exclude_conversation_id = None if conversation_id else current_session_scope()`에서, 세션이 없을 때 나오는 **기본값(sentinel)**을 그대로 "제외 대상"으로 넘기고 있다. 멘토님이 "이 기본값이 언제 나오고, 그때 제외가 맞냐"고 물으셨다.
- 시도
    - 값의 출처를 **호출 흐름으로 추적**.
    - 기본값은 ContextVar가 비었을 때 나오고, 그걸 채우는 건 `agent_runtime`의 `run_agent`/`stream_agent`뿐.
    - 즉 기본값은 **그 경로를 안 거치는 실행(테스트·도구 직접 호출)**에서만 나온다.
- 해결
    - 실제 대화 id는 항상 `conv_...`라 기본값과 **절대 겹치지 않음**
    - 넘겨도 걸러지는 대화가 없어 동작상 버그 아님(무해한 no-op).
    - 다만 "세션 없음 = 제외할 현재 대화 없음"이라, sentinel 대신 **`None`(아무것도 제외 안 함)**으로 의도를 명시하도록 고쳤다.
- 배운 점과 아쉬운 점
    - **"동작상 문제 없음"과 "의도가 코드에 드러남"은 다르다.** 우연(id가 안 겹침)에 기대는 코드는 나중에 계약이 깨지면 조용히 문제가 된다. 이건 버그 수정이 아니라 "의도 명확화"라는 걸 정직하게 구분해 답변하는 것도 배웠다.
