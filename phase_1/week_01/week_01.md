## 📚 이번 주 학습한 것

### 1. Agentic AI가 무어냐?
- Agentic AI는 특정 프롬프트에 대한 문자(토큰)들을 단순히 예측하는 자연어 답변뿐만 아니라, 능동적인 역할을 한다.
- 자연어 답변, 특정 행동에 대한 도구들을 사용하며 이제 `사람`처럼 행동한다.
- 원래는 목표을 위한 행동을 AI에게 물어보면 그에 대해서 자연어로 답변만 해줬었는데, AI가 직접 목표를 위한 행동을 한다는 거다. 다르게 말하면 비서와 같은 역할인 것이다.
- 1단계에서는 우리의 비서(?)를 완성해나가는 게 목표다. 사람이 뭘 해달라고 명령하면 직접 도구(코드)를 가져다 쓰면서 목표에 도달하는 셈인 거다!
- 그러기 위해서는 AI가 어떤 도구들이 있는지를 알아야 하고, 그렇다면 그걸 어떻게 AI가 인식할 수 있게 만들건지, 그리고 그 도구에 허점이 있진 않은지를 잘 고려해야 한다. 이건 행동에 대한 결과의 퀄리티 문제로 이어지기 때문이다!

### 2. Agentic AI 제작을 위한 환경 구성

#### 1. WSL(Windows Subsystem for Linux)
- WSL은 Windows 환경에서 Linux를 사용할 수 있도록 만든 프로그램이다.
- 기존에는 Hyper-V와 같은 가상화 기능으로 이를 구현하였지만 그리 좋은 경험은 아니여서 대부분 VMWare와 같은 가상화 프로그램을 별도로 사용하여 오버헤드를 감수하며 사용했었다.
- 이러한 수요에 맞춰 Windows에서 더 나은 가상 리눅스를 사용할 수 있게 해주었고, 사용해보니 무거운 작업만 아니면 Native처럼 사용할 수 있었다.

#### 2. Github CLI를 통한 인증 관리
- 원래 Github에서 명령어로 clone, commit, push, fetch 등을 권한이 있어야 실행 가능했다면 별도의 Token 설정을 했어야 했다.
- Github CLI는 HTTPS 형식으로 인증을 인가하며, 웹페이지로 로그인하고 인증 번호를 입력하면 로그인이 되고 Token이 발급되는 형식이다.
- 이런게 있었으면 진작 사용했을텐데... 왜 항상 Token 수동 발급받고 쓰다가 만료되서 꼬이고... 이젠 아주 간편하다! 

#### 3. Rust 기반의 uv
- 원래 Python에서 개발을 위한 환경을 구성할 때는 가상 환경을 사용했었다.
- Docker를 사용해도 되는 거였겠지만, 사실 실제 서버에 올려서 개발할 게 아니면 Docker로만 개발을 시작하는 건 좀 번거롭다. 아니면 익숙하지 않아서인 이유도 있곘지만.
- `uv`는 Rust 언어 기반으로 만들어진 Python 생태계 패키지 관리 도구로, 압도적인 속도와 편의성을 제공한다.
- 이런 게 있었으면 진작 사용헀을텐데(2)... 환경 구성에 대한 스트레스가 훨씬 줄었다!

#### 4. API 키 발급
- API 키 발급은 카카오테크캠퍼스의 AI Cloud에서 ChatGPT API 키를 발급받을 수 있었다.
- 일주일 단위로 발급받는게 가장 안전(?)하지 않을까 싶다. 설마 `.env` 파일을 Github에 업로드하는 실수를 할까 하는 생각이지만 사람 일은 모르지만..
- API 키를 발급받아서 직접 사용해보는 건 처음이라 엄청 신기했다. 외부 API에 의존하는 프로그램을 만들어보니까 이제야 진짜 개발자가 된 느낌이다!

### 3. 스케줄 CRD(추가, 조회, 삭제) 도구를 만들어보자!
- 이번 Week 1의 목표는 AI(LLM)이 직접 사용할 수 있는 도구를 만드는 것이다!
- 사실 LangChain 등 기반의 구조를 몰라도 이미 짜여져있는 코드에서 도구 부분만 구현하면 된다.
- `personal_create_schedule()`
    - 추가할 개인 일정을 현재 대화의 임시 메모리에 생성(PERSONAL_SCHEDULES 리스트에 추가)하는 역할을 한다.
    - 예를 들어, `"7월 6일 오전 10시에 1주차 학습일지 제출이라는 일정을 만들어줘"`라고 하면 LLM이 이 자연어를 특정 규격으로 가공해서 해당 도구를 사용해 일정을 추가한다.
    - 다양한 파라미터를 통해 현재 세션에서만 유효하도록 하기 위해 헬퍼 함수를 사용할 수 있었다.
    - 이렇게 추가된 일정은 서버를 리부팅하면 없어져버리지만, 일단 AI가 이 도구를 사용해서 일정을 알아서 저장했다는 게 놀라웠다!
- `personal_list_schedules()`
    - 선택한 시작일과 종료일 범위에 포함되는 개인 일정을 조회하는 역할을 한다.
    - 예를 들어, `"내일 무슨 일정들이 있어?"`라고 하면 LLM이 저장된 내일 일정을 조회해서 자연어 형태로 답변을 한다.
    - 현재 세션 범위의 일정을 모두 조회, date_from 이상만을 필터링, date_to 이하만을 필터링 해서 조건을 만족하고, json으로 반환한다. 정확히는 json 포멧의 데이터는 LLM이 받아 자연어로 답해주는 형식이다.
    - 해당 도구는 사용자(의뢰자)가 단순히 조회해달라고 물어보기 위해 쓰이거나, 다음에 오는 일정 삭제 도구에 필요한 일정 ID를 알기 위해 쓰인다. 즉 조회 도구가 구현되지 않으면 삭제 도구는 사용할 수 없다!
- `personal_delete_schedule()`
    - 특정 일정을 ID 기준으로 검색해서 삭제하는 역할을 한다.
    - 특정 일정의 ID는 사용자와 LLM 모두가 모르기 때문에, 사용자가 의뢰한 기간 또는 주제에 부합하는 일정들을 `personal_list_schedules()`를 통해 조회하여 얻은 ID를 통해 삭제한다.

### 4. 프롬프트가 중요하구나!
- 위 세 개의 도구를 구현하고나서 사용해봤는데, 생각보다 성능이 그리 좋지 못했다.
- 테스트 케이스 10개 가량을 Claude Code를 통해 생성해서 테스트 해보았는데, 처음에는 10개 중에 5개 정도로 비교적 조건이 간단하고 날짜가 명확한 테스트 케이스만 통과했다.
- 예를 들어, 오늘이 일요일이라 가정헀을 때 `"월요일부터 4주간 오전 10시에 일정을 잡아줘"`라고 한다면 "월요일"의 기준이 이번주인지 다음주인지 헷갈려했다.
- 원인을 조사해보니, LLM(ChatGPT)이 API 키를 통한 호출을 처리해주는 OpenAI의 서버 시간을 활용하거나, 해당 파일에 구현돼있진 않아 보이지만 이 구조 어딘가에 시간을 프롬프트로 보내주는 게 있을 거라 판단했으나 없었다.
- 그리고 만들어둔 도구들을 사용하지 않고 LLM 순수 피지컬(?)로 일정을 기억하고 추가하거나 삭제하는 문제들도 있었다. 이는 Trace를 보면서 알 수 있었다.
- 결국 LLM은 시간 의뢰를 받았지만 사용자의 시간이 언젠지를 정확히 찾아내지 못하는 문제와 더불어 지 맘대로(?) 세션 내에 있는 리스트에 일정을 추가/조회/삭제하는 방식이 아니라 자기 스스로 캐싱을 하는 모습을 보였다. 
- 사용자의 현재 시간과 더불어, "너는 Nana야. 사용자의 개인 일정을 관리하는 AI 비서야", "일정 생성/조회/삭제는 반드시 tool을 호출해라.", "Tool 없이 직접 답변하지 마라.", "날짜 계산 시 오늘 요일 기준으로 며칠 후인지 순서대로 계산하라" 등의 아주 구체적인 프롬프트와 더불어, 원래는 Todo 구현 박스 바깥은 건들면 안되는 거겠지만 임의로 오늘 요일과 시간을 담은 프롬프트도 넣었다.
- 이러한 프롬프트 고도화를 통해 테스트 케이스 10개 중에 9개를 통과하는 쾌거(?)를 이루었다. 나머지 1개는 너무 복잡한 자연어로 줘서 모델이 계산을 계속 잘못하는 듯 하다.
- 도구를 효율적이고 정확하게 짜는 것도 중요하겠지만, 제일 중요한 것은 아무리 좋은 모델이라도 프롬프트가 이상하면 결과도 이상하게 나오고, 반대로 모델이 좋지 않아도 프롬프트가 명확하고 좋다면 결과가 비교적 아주 좋게 나온다. 이 차이가 참 심하다는 걸 알았다!
