# 1. 네트워크 백그라운드

## 1.1 OSI 7 Layer가 필요한 이유

OSI 7계층은 **복잡한 네트워크의 상호 연결 구조를 표준화하기 위한 참조 모델**이다.

과거에는 장치와 장치가 서로 다른 구조를 가지고 있어 네트워크 연결이 어려웠다. 이를 해결하기 위해 ISO에서 네트워크 동작을 계층별로 나누어 설명하는 표준 모델을 만들었다.

핵심은 다음과 같다.

| 목적 | 설명 |
|---|---|
| 표준화 | 서로 다른 장치와 시스템이 통신할 수 있도록 공통 기준 제공 |
| 역할 분리 | 네트워크 전체 동작을 7개의 계층으로 나누어 이해 |
| 문제 분석 | 네트워크 장애가 어느 계층에서 발생했는지 추적 가능 |
| 확장성 | 한 계층의 기술이 바뀌어도 다른 계층에 미치는 영향을 줄임 |

자료의 OSI 7계층 그림은 송신자가 데이터를 보낼 때 상위 계층에서 하위 계층으로 내려가며 헤더가 붙고, 수신자는 반대로 하위 계층에서 상위 계층으로 올라가며 헤더를 해석하는 구조를 보여준다. 이것을 **캡슐화와 역캡슐화**로 이해하면 된다.

---

## 1.2 OSI 7계층 요약

| 계층 | 이름 | 핵심 역할 | 대표 개념 |
|---|---|---|---|
| 7계층 | 응용 계층 | 애플리케이션이 네트워크를 사용하는 방법 제공 | HTTP, HTTPS, DNS, SSH |
| 6계층 | 표현 계층 | 데이터 형식 변환, 인코딩, 암호화, 압축 | 문자 인코딩, 암호화, 압축 |
| 5계층 | 세션 계층 | 논리적 연결인 세션 수립, 유지, 종료 | 세션, 동기화, 반이중/전이중 |
| 4계층 | 전송 계층 | 프로세스 간 통신, 신뢰성/속도/보안 제공 | TCP, UDP, TLS, Port |
| 3계층 | 네트워크 계층 | 서로 다른 네트워크 간 패킷 전달 | IP, 라우터, ICMP |
| 2계층 | 데이터링크 계층 | 같은 LAN 내 장치 식별과 프레임 전달 | MAC 주소, Ethernet, ARP, Switch |
| 1계층 | 물리 계층 | 비트를 전기적/물리적 신호로 전달 | 케이블, 허브, 리피터, NIC |

실무에서는 OSI 모델을 그대로 구현한다기보다, 네트워크 문제를 설명하는 기준으로 많이 쓴다.

예를 들어 웹 서버 접속이 안 될 때는 다음처럼 계층별로 점검할 수 있다.

| 증상 | 의심 계층 |
|---|---|
| 랜선이 빠져 있음 | 1계층 물리 계층 |
| MAC 주소 충돌, 스위치 문제 | 2계층 데이터링크 계층 |
| IP 라우팅 문제, 게이트웨이 문제 | 3계층 네트워크 계층 |
| 포트가 막힘, TCP 연결 실패 | 4계층 전송 계층 |
| DNS, HTTP, HTTPS 문제 | 7계층 응용 계층 |

---

## 1.3 TCP/IP 모델

실제 인터넷은 OSI 7계층보다 **TCP/IP 모델**에 더 가깝게 동작한다.

자료의 TCP/IP 모델 그림은 OSI 7계층을 4개의 계층으로 단순화해 비교한다.

| OSI 모델 | TCP/IP 모델 | 설명 |
|---|---|---|
| 7 응용, 6 표현, 5 세션 | 응용 계층 | 애플리케이션 통신 규칙 |
| 4 전송 | 전송 계층 | TCP/UDP 기반 프로세스 간 통신 |
| 3 네트워크 | 인터넷 계층 | IP 기반 호스트 간 통신 |
| 2 데이터링크, 1 물리 | 네트워크 액세스 계층 | 실제 네트워크 매체 접근 |

즉, OSI는 학습과 설명을 위한 참조 모델이고, TCP/IP는 실제 인터넷 프로토콜 스택에 가깝다.

# 2. 하위 계층: 물리, 데이터링크, 네트워크

## 2.1 1계층: 물리 계층

물리 계층은 **비트를 실제 전기 신호나 물리적 신호로 바꾸어 전달하는 계층**이다.

| 항목 | 내용 |
|---|---|
| 관심사 | 신호를 어떻게 물리적으로 전달할 것인가 |
| PDU | 비트 |
| 주요 장비 | 허브, 리피터, NIC, 케이블, 커넥터 |
| 특징 | 목적지 판단보다 신호 전달 자체에 집중 |

쉽게 말해, 물리 계층은 “데이터가 어디로 가야 하는지”보다는 “신호가 끊기지 않고 전달되는지”에 관심을 둔다.

---

## 2.2 2계층: 데이터링크 계층

데이터링크 계층은 **LAN 내부에서 누가 누구에게 데이터를 보내는지 식별하고, 전송 과정의 오류를 검출하는 계층**이다.

| 항목 | 내용 |
|---|---|
| 관심사 | 같은 네트워크 안에서 장치 간 데이터 전달 |
| PDU | 프레임 |
| 주요 주소 | MAC 주소 |
| 주요 장비 | NIC, 스위치, 브릿지 |
| 주요 프로토콜 | Ethernet, ARP, RARP |

데이터링크 계층에서는 프레임에 송신자와 수신자의 MAC 주소가 기록된다.

---

## 2.3 NIC와 MAC 주소

NIC(Network Interface Card)는 **LAN과 컴퓨터를 연결하는 하드웨어 장치**다.

다른 이름으로는 랜 카드, 이더넷 카드, 네트워크 어댑터 등이 있다.

NIC는 고유 식별자인 **MAC 주소**를 가진다.

| 항목 | 설명 |
|---|---|
| MAC 주소 | NIC에 할당된 고유 식별자 |
| 길이 | 48비트, 6바이트 |
| 표기 | 16진수 6묶음으로 표기 |
| 예시 | `C3-C1-E8-85-54-FE` |
| 용도 | LAN 내 장치 식별 |

자료의 MAC 주소 그림은 앞부분이 제조사 식별 번호, 뒷부분이 장치 식별 번호로 나뉘는 구조를 보여준다.

확인 명령어 예시는 다음과 같다.

```bash
# Windows
ipconfig /all

# macOS
networksetup -listallhardwareports
```

---

## 2.4 3계층: 네트워크 계층

네트워크 계층은 **서로 다른 네트워크 간 데이터를 전달하는 계층**이다.

| 항목 | 내용 |
|---|---|
| 관심사 | 목적지까지 어떤 경로로 보낼 것인가 |
| PDU | 패킷 |
| 주요 주소 | IP 주소 |
| 주요 장비 | 라우터 |
| 주요 프로토콜 | IP, ICMP, IGMP |

같은 LAN 내부에서는 MAC 주소가 중요하지만, 서로 다른 네트워크를 건너갈 때는 IP 주소와 라우터가 중요하다.

---

## 2.5 Internet Protocol, IP

IP는 **서로 다른 네트워크 간 데이터 통신을 위해 정한 규약의 집합**이다.

IP의 중요한 성질은 다음 두 가지다.

| 성질 | 의미 |
|---|---|
| 비신뢰성 | 패킷이 중간에 유실될 수 있음 |
| 비연결성 | 송신자와 수신자를 미리 연결하지 않고, 패킷에 목적지만 적어 전송 |

즉, IP는 “목적지까지 최대한 보내는 것”에 집중한다. 데이터가 반드시 도착하는지, 순서대로 도착하는지까지 보장하지 않는다. 이 부분은 TCP 같은 4계층 프로토콜이 담당한다.

IP 패킷 헤더에는 Source Address와 Destination Address가 들어간다. 이것이 송신 호스트와 수신 호스트를 식별하는 핵심 정보다.

# 3. IP 주소, 서브넷, CIDR

## 3.1 IPv4 주소

IP 주소는 **네트워크에 연결된 장치를 식별하기 위해 부여되는 주소**다.

IPv4는 32비트 주소 체계다.

예시:

```text
172.16.254.1
```

이를 2진수로 표현하면 다음처럼 8비트씩 4개 옥텟으로 나뉜다.

```text
10101100.00010000.11111110.00000001
```

| 항목 | 값 |
|---|---|
| IPv4 길이 | 32비트 |
| 옥텟 | 8비트 = 1바이트 |
| 한 옥텟 범위 | 0-255 |
| 전체 주소 수 | 2^32, 약 43억 개 |

IPv4는 약 43억 개 주소를 만들 수 있지만, 인터넷 사용자가 폭증하고 주소가 비효율적으로 분배되면서 고갈 문제가 생겼다.

---

## 3.2 IP 주소 클래스

초기에는 IP 주소를 클래스 단위로 나눠 할당했다.

| 클래스 | 호스트 수 | 용도 |
|---|---:|---|
| A 클래스 | 약 1600만 개 | 대규모 조직, 정부 기관 |
| B 클래스 | 약 65000개 | 중간 규모 기업 |
| C 클래스 | 254개 | 소규모 조직 |

이 방식은 조직 규모에 맞춰 주소를 나눠주는 방식이었지만, 여전히 낭비가 많았다.

예를 들어 300개 주소만 필요한 조직에 C 클래스 2개를 주거나, B 클래스를 주면 많은 주소가 남을 수 있다.

---

## 3.3 서브넷

서브넷은 **큰 네트워크를 더 작은 네트워크 단위로 나누는 것**이다.

자료에서는 B 클래스 대역 `172.16.0.0 ~ 172.16.255.255`를 부서별로 나누는 예시를 든다.

| 부서 | 주소 범위 예시 |
|---|---|
| 금융사업부 | 172.16.0.0 ~ 172.16.63.255 |
| 컨설팅사업부 | 172.16.64.0 ~ 172.16.127.255 |
| 교육사업부 | 172.16.128.0 ~ 172.16.191.255 |
| 영업사업부 | 172.16.192.0 ~ 172.16.255.255 |

서브넷의 목적은 주소를 더 효율적으로 쓰고, 네트워크를 논리적으로 분리하는 것이다.

---

## 3.4 서브넷 마스크

서브넷 마스크는 **IP 주소 중 어디까지가 네트워크 부분이고 어디부터가 호스트 부분인지 표시하는 값**이다.

| 값 | 의미 |
|---|---|
| 1 | 네트워크 부분 |
| 0 | 호스트 부분 |

예시:

```text
11111111.11111111.11000000.00000000
255.255.192.0
```

이 경우 앞 18비트가 네트워크를 식별하는 데 사용된다.

---

## 3.5 CIDR

CIDR(Classless Inter-Domain Routing)은 **클래스에 묶이지 않고 더 유연하게 IP 주소 범위를 표현하는 방식**이다.

표기는 다음처럼 한다.

```text
172.16.192.0/18
```

여기서 `/18`은 앞 18비트가 네트워크 부분이라는 뜻이다.

| CIDR | 의미 | 사용 가능한 호스트 수의 감각 |
|---|---|---|
| `/16` | 앞 16비트가 네트워크 | 약 65,534개 |
| `/24` | 앞 24비트가 네트워크 | 약 254개 |
| `/32` | 하나의 IP 주소 | 단일 호스트 지정 |

AWS VPC와 서브넷도 CIDR 방식으로 IP 범위를 정한다.

예시:

```text
VPC:      10.0.0.0/16
Subnet A: 10.0.1.0/24
Subnet B: 10.0.2.0/24
```

---

## 3.6 IPv6

IPv6는 IPv4 주소 부족 문제를 장기적으로 해결하기 위해 등장한 차세대 IP 주소 체계다.

| 항목 | IPv4 | IPv6 |
|---|---|---|
| 길이 | 32비트 | 128비트 |
| 표기 | 10진수 4옥텟 | 16진수, 콜론 구분 |
| 주소 수 | 약 43억 개 | 약 3.4 * 10^38개 |

IPv6 예시:

```text
2001:0db8:85a3:0000:0000:8a2e:0370:7334
```

아직은 IPv4가 많이 사용되며, 점진적으로 IPv6로 전환하는 과정에 있다.

# 4. 공인 IP, 사설 IP, NAT, 라우터

## 4.1 공인 IP와 사설 IP

| 구분 | 공인 IP | 사설 IP |
|---|---|---|
| 사용 범위 | 인터넷 전체 | 내부 네트워크 |
| 고유성 | 전 세계에서 고유 | 해당 사설 네트워크 안에서만 고유 |
| 발급 | ISP가 발급 | 내부 네트워크에서 자체 할당 |
| 외부 접근 | 가능 | 직접 접근 불가 |
| 예시 | `201.106.174.45` | `10.x.x.x`, `172.16.x.x`, `192.168.x.x` |

공인 IP는 인터넷에서 장치나 네트워크를 식별하기 위한 주소다. 반면 사설 IP는 회사나 가정 내부 네트워크에서만 의미가 있다.

가정 공유기에서 흔히 보는 `192.168.0.x` 같은 주소가 사설 IP다.

---

## 4.2 NAT(Network Address Translation)

NAT는 **사설 IP와 공인 IP 사이의 주소를 변환하는 기술**이다.

사설 네트워크 안의 장치가 인터넷에 나가려면, 외부에서는 사설 IP를 알 수 없기 때문에 NAT 장치가 주소를 공인 IP로 바꿔준다.

| NAT 종류 | 설명 |
|---|---|
| SNAT | 내부에서 외부로 나갈 때 출발지 주소 변환 |
| DNAT | 외부에서 내부로 들어올 때 목적지 주소 변환 |
| PAT | IP뿐 아니라 포트 번호까지 활용하여 여러 내부 장치가 하나의 공인 IP를 공유 |

자료의 NAT 그림은 사설 네트워크 내부 장치가 외부 인터넷과 통신하기 위해 NAT 장치를 거치며, 사설 IP가 공인 IP로 변환되는 구조를 보여준다.

AWS에서는 프라이빗 서브넷의 리소스가 인터넷으로 나갈 수 있도록 **NAT 게이트웨이**를 사용한다.

---

## 4.3 라우터와 홉 바이 홉 라우팅

라우터는 **서로 다른 네트워크 사이에서 패킷을 최적 경로로 전달하는 장치**다.

인터넷에는 수많은 라우터가 있고, 각 라우터를 홉(Hop)이라고 부른다.

라우팅 방식은 대략 다음 흐름이다.

1. 패킷이 현재 라우터에 도착한다.
2. 라우터는 라우팅 테이블을 확인한다.
3. 목적지까지 가기 좋은 다음 라우터, 즉 Next Hop을 선택한다.
4. 패킷을 다음 홉으로 전달한다.
5. 이 과정을 반복해 목적지에 도달한다.

자료의 라우터 그림은 각 라우터가 인접 라우터의 상태를 공유하고, 상태가 좋은 홉으로 패킷을 넘기는 과정을 시각화한다.

---

# 5. 전송 계층: Port, TCP, UDP, TLS

## 5.1 4계층 전송 계층

전송 계층은 **종단 간 통신**, 더 정확히는 **프로세스와 프로세스 간 통신**을 담당한다.

3계층 IP는 호스트를 찾아간다. 하지만 하나의 호스트 안에는 여러 프로세스가 실행 중이다. 그래서 어떤 프로세스에게 데이터를 전달할지 식별해야 한다.

이때 사용하는 것이 **포트 번호**다.

---

## 5.2 Port

포트는 **프로세스가 네트워크를 통해 통신할 수 있도록 운영체제로부터 부여받은 식별 번호**다.

예시:

```text
201.16.175.24:8080
```

| 구성 | 의미 |
|---|---|
| `201.16.175.24` | 네트워크 상의 호스트 위치 |
| `8080` | 해당 호스트 안의 프로세스 식별 번호 |

쉽게 말하면 IP는 “건물 주소”, 포트는 “건물 안의 방 번호”에 가깝다.

---

## 5.3 TCP

TCP(Transmission Control Protocol)는 **신뢰성 있는 데이터 전송을 제공하는 4계층 프로토콜**이다.

| 특징 | 설명 |
|---|---|
| 연결 지향 | 통신 전에 연결을 먼저 수립 |
| 신뢰성 | 데이터 누락, 오류를 줄이기 위해 적극적으로 제어 |
| 순서 제어 | 패킷이 순서대로 처리되도록 제어 |
| 흐름 제어 | 수신자가 처리 가능한 만큼만 전송 |
| 오류 제어 | 유실/오류 발생 시 재전송 |
| 혼잡 제어 | 네트워크 혼잡도에 따라 송신량 조절 |

TCP는 신뢰성이 중요한 웹 요청, 파일 전송, 데이터베이스 연결 등에서 많이 사용된다.

---

## 5.4 UDP

UDP(User Datagram Protocol)는 **빠른 전송을 중시하는 4계층 프로토콜**이다.

| 특징 | 설명 |
|---|---|
| 비연결형 | TCP처럼 연결을 먼저 수립하지 않음 |
| 낮은 오버헤드 | 제어 과정이 적어 빠름 |
| 신뢰성 미보장 | 순서, 재전송, 흐름 제어를 기본 제공하지 않음 |
| 활용 분야 | 스트리밍, 화상 회의, 온라인 게임 등 실시간 서비스 |

UDP는 빠르지만, 데이터 유실이나 순서 문제는 애플리케이션 레벨에서 직접 처리해야 한다.

---

## 5.5 IP vs UDP vs TCP

자료의 비교표를 정리하면 다음과 같다.

| 구분 | IP | UDP | TCP |
|---|---|---|---|
| 전달 대상 | 호스트 - 호스트 | 프로세스 - 프로세스 | 프로세스 - 프로세스 |
| OSI 계층 | 3계층 | 4계층 | 4계층 |
| 연결성 | 없음 | 없음 | 있음 |
| 신뢰성 | 없음 | 없음 | 있음 |
| 비유 | 건물 앞까지 효율적으로 배달 | 사람에게 빠르게 전달 | 사람에게 안전하게 전달 |

즉, IP는 목적지 호스트까지 가는 역할, UDP/TCP는 해당 호스트 안의 프로세스까지 전달하는 역할을 한다.

---

## 5.6 TLS

TLS(Transport Layer Security)는 **네트워크 통신에 기밀성, 무결성, 인증을 제공하는 보안 프로토콜**이다.

초기에는 SSL이라는 이름으로 시작했지만, 이후 TLS로 표준화되었다.

| 보안 속성 | 의미 |
|---|---|
| 기밀성 | 중간에 데이터가 탈취되어도 내용을 알 수 없도록 암호화 |
| 무결성 | 데이터가 전송 중 변조되지 않았는지 확인 |
| 인증 | 통신 상대가 의도한 서버인지 확인 |

TLS 흐름은 대략 다음과 같다.

1. 클라이언트와 서버가 TLS Handshake를 수행한다.
2. 클라이언트는 서버 인증서를 통해 서버를 검증한다.
3. 양쪽이 사용할 암호화 알고리즘을 협의한다.
4. 대칭키를 생성한다.
5. 이후 데이터는 암호화되어 전송된다.
6. 수신 측은 데이터 변조 여부를 확인한다.

HTTPS는 HTTP에 TLS를 결합한 것이다.

```text
HTTPS = HTTP + TLS
```

---

# 6. 상위 계층: 세션, 표현, 응용

## 6.1 5계층 세션 계층

세션 계층은 **송수신 측 사이의 논리적 연결인 세션을 수립, 유지, 종료하는 계층**이다.

| 역할 | 설명 |
|---|---|
| 세션 수립 | 클라이언트와 서버 통신 시작 시 논리적 연결 설정 |
| 세션 유지 | 통신 중 연결 상태 관리 |
| 세션 종료 | 전송 완료 후 연결 종료 |
| 대화 방식 관리 | 반이중, 전이중 통신 관리 |
| 동기화 | 장애 발생 시 복구 지점 관리 |

---

## 6.2 6계층 표현 계층

표현 계층은 **데이터 형식을 관리하고 변환하는 계층**이다.

| 기능 | 설명 |
|---|---|
| 인코딩/디코딩 | 데이터를 다른 장치에서도 해석 가능한 형식으로 변환 |
| 암호화/복호화 | 데이터를 보호하기 위해 변환 |
| 압축/압축 해제 | 전송 효율을 높이기 위해 데이터 크기 축소 |

---

## 6.3 7계층 응용 계층

응용 계층은 **애플리케이션과 네트워크 사이의 인터페이스를 제공하는 계층**이다.

대표 프로토콜은 다음과 같다.

| 프로토콜 | 역할 |
|---|---|
| HTTP | 웹 요청/응답 |
| HTTPS | TLS가 적용된 웹 요청/응답 |
| DNS | 도메인 이름을 IP 주소로 변환 |
| SSH | 원격 서버 접속 |

브라우저에서 `https://elice.io/kr`에 접속하면 대략 다음 과정이 일어난다.

1. DNS를 통해 도메인을 IP 주소로 변환한다.
2. 서버와 TCP 연결을 맺는다.
3. HTTPS라면 TLS Handshake를 수행한다.
4. HTTP 요청을 보낸다.
5. 서버가 응답을 반환한다.

# 7. 클라우드 컴퓨팅 및 AWS 소개

## 7.1 IT 인프라란?

IT 인프라는 애플리케이션을 실행하고 서비스를 제공하기 위해 필요한 기반 자원 전체를 의미한다.

대표 구성 요소는 다음과 같다.

| 구성 요소 | 예시 |
|---|---|
| 서버 | CPU, RAM, OS가 있는 컴퓨팅 자원 |
| 스토리지 | 파일, 객체, 디스크 저장 공간 |
| 네트워크 | IP, 라우팅, 방화벽, 로드밸런서 |
| 데이터베이스 | MySQL, PostgreSQL, Oracle 등 |
| 보안 | 인증, 권한, 암호화, 방화벽 |
| 운영 도구 | 모니터링, 로그, 백업, 배포 자동화 |

---

## 7.2 온프레미스 vs 클라우드

| 구분 | 온프레미스 | 클라우드 |
|---|---|---|
| 비용 | 초기 구축 및 유지보수 비용이 높음 | 상대적으로 저렴하게 시작 가능 |
| 탄력성 | 확장/축소가 어려움 | 필요한 만큼 확장/축소 용이 |
| 보안 통제 | 직접 통제 가능 | 공급자가 관리하는 영역 존재 |
| 성능 최적화 | 자유도가 높음 | 자유도는 상대적으로 낮을 수 있음 |
| 운영 부담 | 장비 구매, 설치, 관리 필요 | 인프라 일부를 공급자가 관리 |

온프레미스는 직접 서버실과 장비를 운영하는 방식이고, 클라우드는 AWS 같은 공급자의 인프라를 빌려 쓰는 방식이다.

---

## 7.3 클라우드 컴퓨팅

클라우드 컴퓨팅은 **클라우드 환경에 인프라를 구성할 수 있도록 IT 자원을 제공해주는 서비스**다.

대표 클라우드 공급자는 다음과 같다.

- AWS
- Microsoft Azure
- Google Cloud Platform
- IBM Cloud
- Oracle Cloud

---

## 7.4 IaaS, PaaS, SaaS

클라우드 서비스 유형은 공급자가 어디까지 관리해주는지에 따라 나뉜다.

| 유형 | 이름 | 사용자가 주로 관리하는 것 | 예시 감각 |
|---|---|---|---|
| IaaS | Infrastructure as a Service | OS, 런타임, 미들웨어, 데이터, 애플리케이션 | EC2 같은 가상 서버 |
| PaaS | Platform as a Service | 데이터, 애플리케이션 | Heroku, Elastic Beanstalk 감각 |
| SaaS | Software as a Service | 거의 사용만 함 | Gmail, Notion, Slack 감각 |

자료의 관리 범위 그림은 On-Premise에서 SaaS로 갈수록 클라우드 공급자가 관리하는 범위가 넓어지는 구조를 보여준다.

---

## 7.5 Public, Private, Hybrid Cloud

| 모델 | 설명 | 특징 |
|---|---|---|
| Public Cloud | 클라우드 제공자가 구축, 소유, 관리 | 불특정 다수가 공유 자원을 사용, 비용 저렴, 확장 용이 |
| Private Cloud | 기업 또는 조직이 구축, 소유, 관리 | 특정 사용자만 독점 사용, 보안 통제 강함, 비용 높음 |
| Hybrid Cloud | Public과 Private을 함께 사용 | 민감 자원은 Private, 확장 자원은 Public처럼 조합 가능 |

AWS는 대표적인 Public Cloud 서비스다.

자료에서 다루는 주요 라인업은 다음과 같다.

# 8. AWS 글로벌 인프라: 리전, 가용 영역, 엣지 로케이션

## 8.1 리전(Region)

리전은 **전 세계에서 데이터 센터를 클러스터링하는 물리적 위치**다.

예시:

```text
ap-northeast-2  # 서울 리전
```

리전의 특징은 다음과 같다.

| 특징 | 설명 |
|---|---|
| 지리적 위치 | 서울, 도쿄, 버지니아 북부 등 주요 국가/도시에 위치 |
| 격리성 | 각 리전은 다른 리전과 격리 |
| 장애 영향 | 한 리전 장애가 다른 리전에 직접 영향을 주지 않도록 설계 |
| 선택 기준 | 서비스 대상 사용자와 가까운 리전을 선택하는 것이 지연 시간 측면에서 유리 |

자료 기준으로 2026년 4월에는 39개의 리전이 있다고 설명한다.

---

## 8.2 가용 영역(Availability Zone, AZ)

가용 영역은 **리전 안에 있는 개별 데이터 센터 단위**다.

예시:

```text
ap-northeast-2a
ap-northeast-2b
```

| 특징 | 설명 |
|---|---|
| 물리적 격리 | 각 AZ는 독립된 전원, 냉각, 인프라를 가짐 |
| 고속 연결 | 같은 리전 내 AZ끼리는 전용 광 네트워크로 연결 |
| 고가용성 | 여러 AZ에 분산하면 단일 데이터 센터 장애에 강함 |
| 확장성 | 부하를 여러 AZ로 분산 가능 |

자료 기준으로 2026년 4월에는 123개의 가용 영역이 있다고 설명한다.

---

## 8.3 엣지 로케이션(Edge Location)

엣지 로케이션은 **사용자에게 콘텐츠를 더 빠르게 전달하기 위한 캐시 서버 거점**이다.

| 항목 | 설명 |
|---|---|
| 목적 | 사용자와 가까운 위치에서 콘텐츠 제공 |
| 방식 | 원본 서버 데이터를 엣지에 캐싱 |
| 효과 | 물리적 거리 감소, 응답 속도 향상 |
| 대표 서비스 | CloudFront, Route 53 |

CloudFront는 이미지, 영상, HTML 같은 콘텐츠를 전 세계 엣지에 캐싱하여 전달하는 CDN 서비스다. Route 53은 전 세계에 분산된 DNS 서버를 통해 도메인 이름을 IP 주소로 변환한다.

---

## 8.4 단일 AZ vs 다중 AZ

자료의 시나리오는 서울 지역에 폭우가 내려 특정 AZ가 중단된 상황을 가정한다.

| 구분 | 단일 AZ 운영 | 다중 AZ 운영 |
|---|---|---|
| 서비스 배치 | 하나의 데이터 센터에서만 운영 | 여러 데이터 센터에 분산 운영 |
| 장애 발생 시 | 서비스 전체 중단 가능 | 다른 AZ가 트래픽을 받아 정상 운영 가능 |
| 데이터 상태 | 같은 AZ에 백업이 있으면 복구 지연 또는 유실 위험 | 다른 AZ의 복제본으로 빠른 복구 가능 |

핵심은 **장애는 막을 수 없어도, 장애가 서비스 전체 중단으로 이어지지 않게 설계할 수 있다**는 점이다.

---

# 9. AWS VPC

## 9.1 VPC란?

VPC(Virtual Private Cloud)는 **AWS 퍼블릭 클라우드 안에 구성하는 독립적인 클라우드 네트워크**다.

| 항목 | 설명 |
|---|---|
| 개념 | 물리적 네트워크가 아니라 논리적 네트워크 |
| 범위 | 특정 리전에 속함 |
| 독립성 | 한 리전 안에 여러 VPC를 만들 수 있고, 각 VPC는 독립적 |
| 확장 | 다른 리전의 VPC와 연결해 네트워크 확장 가능 |

VPC는 AWS에서 서버, DB, 로드밸런서 같은 리소스가 서로 통신하는 기본 네트워크 경계다.

---

## 9.2 서브넷과 가용 영역

AWS에서 서브넷은 **가용 영역과 1:1 관계**다.

즉, 하나의 서브넷은 하나의 AZ에만 속한다.

| 서브넷 종류 | 설명 |
|---|---|
| 퍼블릭 서브넷 | VPC 내부 리소스 및 외부 인터넷과 통신 가능 |
| 프라이빗 서브넷 | VPC 내부 리소스와 통신 가능, 외부 인터넷과 직접 통신 불가 |

자료의 서브넷 그림은 하나의 VPC 안에 여러 AZ가 있고, 각 AZ 안에 퍼블릭/프라이빗 서브넷이 배치되는 구조를 보여준다.

---

## 9.3 VPC와 서브넷의 CIDR

VPC와 서브넷은 모두 CIDR로 IP 범위를 지정한다.

예시:

```text
VPC_A:    10.0.0.0/16
Subnet_a: 10.0.1.0/24
Subnet_b: 10.0.2.0/24
```

| CIDR | 의미 |
|---|---|
| `10.0.0.0/16` | VPC 전체 주소 범위 |
| `10.0.1.0/24` | VPC 내부의 한 서브넷 주소 범위 |
| `10.0.2.0/24` | VPC 내부의 다른 서브넷 주소 범위 |

VPC가 큰 주소 공간을 가지고, 그 안을 여러 서브넷으로 쪼개는 구조다.

---

## 9.4 가상 라우터와 라우팅 테이블

AWS VPC에는 가상 라우터가 존재하며, 라우팅 테이블을 통해 트래픽의 목적지를 결정한다.

예시 라우팅 테이블:

| 목적지 | 타겟 | 의미 |
|---|---|---|
| `10.0.0.0/16` | `local` | VPC 내부 통신 |
| `0.0.0.0/0` | 인터넷 게이트웨이 | 그 외 모든 IPv4 목적지는 인터넷으로 보냄 |

`local` 경로는 VPC 내부 리소스끼리 통신하기 위한 기본 경로다.

`0.0.0.0/0`은 “어디든”이라는 뜻의 기본 경로로, 인터넷 방향 라우팅에 자주 사용된다.

---

## 9.5 인터넷 게이트웨이(Internet Gateway)

인터넷 게이트웨이는 **VPC 내부 리소스가 외부 인터넷과 통신할 수 있도록 연결을 제공하는 구성 요소**다.

퍼블릭 서브넷이 되려면 보통 다음 조건이 필요하다.

1. VPC에 인터넷 게이트웨이가 연결되어 있어야 한다.
2. 서브넷의 라우팅 테이블에 `0.0.0.0/0 -> 인터넷 게이트웨이` 경로가 있어야 한다.
3. 인스턴스에 퍼블릭 IP가 있어야 한다.
4. 보안 그룹/NACL에서 트래픽이 허용되어야 한다.

자료의 VPC-타 네트워크 연결 그림은 퍼블릭 서브넷의 라우팅 테이블이 인터넷 게이트웨이를 향하도록 설정되는 구조를 보여준다.

---

## 9.6 NAT 게이트웨이

프라이빗 서브넷은 외부 인터넷과 직접 통신하지 못한다. 하지만 OS 패키지 설치, 외부 API 호출 등 인터넷으로 “나가는” 통신이 필요할 수 있다.

이때 사용하는 것이 **NAT 게이트웨이**다.

| 항목 | 설명 |
|---|---|
| 위치 | 퍼블릭 서브넷에 위치 |
| 역할 | 프라이빗 서브넷 리소스의 사설 IP를 퍼블릭 IP로 변환 |
| 통신 방향 | 내부에서 외부로 나가는 통신을 가능하게 함 |
| 보안 효과 | 외부에서 프라이빗 인스턴스로 직접 접근하는 것은 막으면서, 내부에서 필요한 외부 통신은 가능하게 함 |

프라이빗 서브넷의 라우팅 테이블 예시는 다음과 같다.

| 목적지 | 타겟 |
|---|---|
| `10.0.0.0/16` | `local` |
| `0.0.0.0/0` | NAT 게이트웨이 |

---

## 9.7 보안 그룹과 네트워크 ACL

VPC는 네트워크 보안을 위해 두 가지 가상 방화벽 기능을 제공한다.

| 구분 | 보안 그룹(Security Group) | 네트워크 ACL(Network ACL) |
|---|---|---|
| 적용 범위 | 인스턴스 수준 | 서브넷 수준 |
| 제어 대상 | 인스턴스로 들어오고 나가는 트래픽 | 서브넷으로 들어오고 나가는 트래픽 |
| 상태 | 상태 기반(Stateful) | 비상태 기반(Stateless) |
| 규칙 평가 | 허용 규칙 중심, 동시 평가 | 번호 순서대로 평가 |
| 허용/거부 | 기본적으로 허용 규칙 중심 | 허용과 거부 규칙 모두 가능 |
| 반환 트래픽 | 인바운드가 허용되면 응답 아웃바운드는 자동 허용 | 인바운드/아웃바운드 모두 별도 허용 필요 |

### 보안 그룹의 핵심

보안 그룹은 상태 기반이다.

예를 들어 인바운드 80번 포트를 허용했다면, 해당 요청에 대한 응답 트래픽은 아웃바운드 규칙을 별도로 엄격하게 맞추지 않아도 처리된다.

### 네트워크 ACL의 핵심

네트워크 ACL은 비상태 기반이다.

인바운드에서 허용한 트래픽이라도, 응답이 나가는 아웃바운드 규칙이 막혀 있으면 통신이 실패할 수 있다.

자료의 비교 그림은 같은 “인바운드 허용” 상황에서도 보안 그룹은 아웃바운드 반환 트래픽을 상태 기반으로 처리하지만, NACL은 아웃바운드 규칙을 별도로 적용한다는 차이를 보여준다.

# 10. AWS 계정, 콘솔, IAM

## 10.1 AWS 프리티어 계정 생성 흐름

자료의 실습은 AWS 사이트에서 계정을 생성하고, 무료 플랜을 선택하고, 결제 정보와 SMS 인증을 거쳐 콘솔에 진입하는 흐름으로 진행된다.

대략적인 흐름은 다음과 같다.

1. AWS 사이트 접속
2. 계정 생성 클릭
3. 이메일 인증
4. 비밀번호 입력
5. 무료 플랜 선택
6. 필수 정보 입력
7. 결제 정보 입력
8. SMS 인증
9. 가입 완료 후 AWS Management Console 진입
10. 로그아웃 후 다시 로그인 실습

자료 기준 프리티어 정책은 2025년 7월 15일 이전/이후 가입에 따라 구조가 달라진다고 설명한다. 특히 무료 플랜은 평가용이며, 만료 및 Paid Plan 전환 조건을 확인해야 한다고 정리되어 있다.

---

## 10.2 콘솔에서 확인할 것

AWS 콘솔 실습에서는 다음을 확인한다.

| 항목 | 의미 |
|---|---|
| 서비스 라인업 | EC2, S3, RDS, VPC, IAM 등 AWS 서비스 탐색 |
| 리전 선택 | 시드니 등 기본 리전에서 서울 리전으로 변경 |
| 청구 비용 확인 | 사용량과 비용, 크레딧 확인 |

AWS는 리전별로 리소스가 나뉘기 때문에, 실습 중에는 반드시 같은 리전을 보고 있는지 확인해야 한다. 예를 들어 EC2를 서울 리전에 만들었는데 콘솔이 시드니 리전을 보고 있으면 인스턴스가 보이지 않는다.

---

## 10.3 IAM이란?

IAM(Identity & Access Management)은 **AWS 리소스 접근을 안전하게 제어하는 서비스**다.

IAM은 다음 질문에 답한다.

```text
누가, 어떤 리소스에 대해, 어떤 작업을 할 수 있는가?
```

핵심 원칙은 **최소 권한 원칙**이다.

즉, 사용자나 서비스가 필요한 작업을 수행할 만큼만 권한을 부여해야 한다.

---

## 10.4 Root와 IAM User

| 구분 | 설명 | 권장 사용 |
|---|---|---|
| Root | 계정 생성 시 만들어지는 최고 권한 사용자 | 일상 작업에 사용하지 않음 |
| IAM User | 실제 작업을 위해 생성하는 개별 계정 | 필요한 권한만 부여해 사용 |

Root 계정은 모든 권한을 가진 슈퍼 유저이므로, 반드시 MFA를 설정하고 평소에는 IAM User로 작업하는 것이 안전하다.

---

## 10.5 IAM Group

IAM Group은 **사용자를 직무나 역할 단위로 묶어 권한을 표준화하는 기능**이다.

예를 들어 다음처럼 그룹을 나눌 수 있다.

| 그룹 | 권한 예시 |
|---|---|
| Developers | EC2 조회, 로그 확인, 제한적 배포 권한 |
| DBAdmins | RDS 관리 권한 |
| ReadOnly | 대부분 리소스 읽기 전용 |

사용자는 여러 그룹에 속할 수 있고, 속한 그룹들의 권한이 합산된다.

---

## 10.6 IAM Policy

Policy는 **IAM에서 무엇을 할 수 있는지 정의하는 JSON 문서**다.

기본적으로 AWS 접근 요청은 거부된다. 정책에 명시적으로 `Allow`가 있어야 접근할 수 있다.

정책의 핵심 요소는 다음과 같다.

| 요소 | 의미 |
|---|---|
| Effect | 허용할지 거부할지 결정. `Allow` 또는 `Deny` |
| Action | 어떤 작업을 허용/거부할지 지정. 예: `s3:GetObject` |
| Resource | 어떤 리소스에 적용할지 ARN으로 지정 |
| Condition | 특정 IP, 시간, MFA 여부 같은 조건 지정 |

예시 감각:

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::example-bucket/*"
}
```

권한은 추상적인 개념이고, 정책은 그 권한을 실제로 적용하기 위한 JSON 문서라고 보면 된다.

---

## 10.7 IAM Role

IAM Role은 **사용자나 서비스가 임시로 맡을 수 있는 권한 묶음**이다.

IAM User는 고정된 자격 증명을 갖지만, Role은 권한이 필요한 주체가 일정 조건에서 맡아 사용하는 방식이다.

| 항목 | 설명 |
|---|---|
| Principal | 누가 이 Role을 맡을 수 있는지 지정 |
| 신뢰 정책 | Role을 맡을 수 있는 주체를 정의 |
| 활용 예 | EC2가 S3에 접근해야 할 때 EC2에 Role 부여 |

실무에서는 액세스 키를 서버에 직접 저장하는 것보다, EC2에 Role을 부여해 AWS 서비스에 접근하게 하는 방식이 더 안전하다.

---

## 10.8 MFA

MFA(Multi-Factor Authentication)는 **비밀번호 외에 추가 인증 수단을 사용하는 보안 방식**이다.

스마트폰 앱이나 물리 보안키에서 일정 주기로 갱신되는 토큰을 사용한다.

Root 계정에는 특히 MFA를 설정하는 것이 중요하다.

---

# 11. AWS EC2

## 11.1 EC2란?

EC2(Elastic Compute Cloud)는 **AWS의 컴퓨팅 자원을 임대하여 가상의 서버를 운영할 수 있는 서비스**다.

| 항목 | 설명 |
|---|---|
| Elastic | 필요에 따라 서버 자원을 확장/축소 가능 |
| Compute | CPU, RAM 같은 컴퓨팅 자원 |
| Cloud | AWS 클라우드 위에서 운영 |
| 과금 | 사용한 만큼 비용 지불 |

EC2 인스턴스는 AWS 퍼블릭 클라우드에서 빌린 가상 서버라고 보면 된다.

---

## 11.2 EC2 인스턴스

EC2 인스턴스는 다음 자원으로 구성된다.

| 자원 | 예시 |
|---|---|
| OS | Amazon Linux, Ubuntu, Windows Server |
| CPU | vCPU 개수 |
| RAM | 메모리 용량 |
| Storage | EBS 루트 볼륨 등 |
| Network | VPC, 서브넷, ENI, Public IP, Private IP |

---

## 11.3 인스턴스 유형과 AMI

EC2 인스턴스를 만들려면 하드웨어 자원과 소프트웨어 자원을 선택해야 한다.

| 구분 | AWS에서 선택하는 항목 | 의미 |
|---|---|---|
| 하드웨어 자원 | 인스턴스 유형 | CPU, RAM, 네트워크, 스토리지 성능 |
| 소프트웨어 자원 | AMI | OS, 기본 소프트웨어, 설정 템플릿 |

---

## 11.4 인스턴스 유형

인스턴스 유형은 다음 요소로 읽을 수 있다.

예시:

```text
t2.micro
```

| 구성 | 의미 |
|---|---|
| `t` | 인스턴스 패밀리 |
| `2` | 세대 |
| `micro` | 크기 |

대표 인스턴스 패밀리는 다음과 같다.

| 패밀리 | 용도 |
|---|---|
| 범용 | 균형 잡힌 CPU/메모리/네트워크 |
| 컴퓨팅 최적화 | 고성능 CPU 필요 워크로드 |
| 메모리 최적화 | 대규모 메모리 데이터 처리 |
| 가속화된 컴퓨팅 | GPU, AI/ML, 고성능 연산 |
| 스토리지 최적화 | 대량 읽기/쓰기 중심 워크로드 |
| HPC 최적화 | 고성능 컴퓨팅 워크로드 |

---

## 11.5 AMI

AMI(Amazon Machine Image)는 **EC2 인스턴스 생성에 필요한 소프트웨어 템플릿**이다.

AMI에는 다음 정보가 포함될 수 있다.

| 구성 | 설명 |
|---|---|
| 루트 볼륨 템플릿 | OS와 기본 소프트웨어 스택 |
| 설정 파일 및 소프트웨어 | 사전 설치 패키지, 설정 |
| 권한 정보 | 인스턴스 시작에 필요한 권한 |
| 볼륨 스냅샷 | 특정 시점의 볼륨 상태 |

---

## 11.6 EC2 네트워킹

EC2 인스턴스는 VPC 안에 생성된다.

주요 네트워크 구성은 다음과 같다.

| 구성 요소 | 설명 |
|---|---|
| VPC | 인스턴스가 속한 논리적 네트워크 |
| 서브넷 | 인스턴스가 배치되는 AZ 단위 네트워크 |
| ENI | Elastic Network Interface, 인스턴스의 가상 네트워크 카드 |
| Private IP | VPC 내부 통신용 IP |
| Public IP | 인터넷에서 직접 접근 가능한 IP |
| 보안 그룹 | 인스턴스 수준 가상 방화벽 |

---

## 11.7 EC2 보안 그룹

EC2 보안 그룹은 **EC2 인스턴스에 설정할 수 있는 가상 방화벽**이다.

예를 들어 FastAPI 서버를 8000번 포트로 실행했다면, EC2 보안 그룹에서 8000번 인바운드 TCP 트래픽을 허용해야 외부 브라우저에서 접근할 수 있다.

---

## 11.8 인스턴스 상태

EC2 인스턴스는 다음 상태를 가진다.

| 상태 | 의미 |
|---|---|
| 대기 중 | 인스턴스 시작 준비 중 |
| 실행 중 | 정상 실행 중 |
| 중지 중 | 중지 처리 중 |
| 중지됨 | 중지된 상태, 다시 시작 가능 |
| 종료 중 | 삭제 처리 중 |
| 종료됨 | 삭제 완료, 복구 불가 |

중지와 종료는 다르다. 중지는 다시 시작할 수 있지만, 종료는 인스턴스를 삭제하는 동작이다.

## 11.9 EC2 SSH 연결

EC2 인스턴스 접속은 SSH를 사용한다.

인스턴스 생성 시 키 페어를 등록하고, 로컬에는 비밀키 `.pem` 파일을 보관한다.

SSH 인증 흐름은 다음과 같다.

1. 클라이언트가 SSH 연결 요청을 보낸다.
2. 서버가 난수를 생성해 클라이언트로 보낸다.
3. 클라이언트는 난수를 비밀키로 암호화해 보낸다.
4. 서버는 공개키로 복호화를 시도한다.
5. 성공하면 SSH 세션이 수립된다.

Windows에서는 MobaXterm 같은 SSH 클라이언트를 사용하고, macOS/Linux에서는 터미널의 `ssh` 명령을 사용할 수 있다.

macOS/Linux에서 키 권한을 제한하는 예시는 다음과 같다.

```bash
chmod 400 AWSStudy.pem
ssh -i AWSStudy.pem ec2-user@<EC2_PUBLIC_DNS_OR_IP>
```

## 11.10 EC2 실습 흐름

자료의 EC2 실습 흐름은 다음과 같다.

1. 키 페어 생성 및 `.pem` 다운로드
2. EC2 인스턴스 생성
3. AMI로 Amazon Linux 2023 선택
4. 인스턴스 유형으로 `t3.micro` 사용

10. SSH 접속


# 12. AWS S3

## 12.1 AWS 스토리지 서비스

AWS의 대표 스토리지 서비스는 다음과 같이 구분된다.

| 종류 | 서비스 | 설명 |
|---|---|---|
| 객체 스토리지 | S3 | 파일을 객체 단위로 저장 |
| 블록 스토리지 | EBS | EC2에 붙는 디스크처럼 사용 |
| 파일 스토리지 | EFS | 여러 인스턴스가 공유 가능한 파일 시스템 |

---

## 12.2 S3란?

S3(Simple Storage Service)는 AWS의 **객체 스토리지 서비스**다.

객체 스토리지는 파일을 폴더/디스크처럼 다루기보다, 객체 단위로 저장하고 HTTP API로 접근하는 방식에 가깝다.

S3의 특징은 다음과 같다.

| 특징 | 설명 |
|---|---|
| 내구성 | 여러 가용 영역에 데이터를 복제해 보관 |
| 확장성 | 저장 용량을 사용자가 직접 디스크 단위로 늘릴 필요 없음 |
| 리전 기반 | 버킷은 특정 리전에 생성 |
| HTTP 기반 접근 | REST API로 객체 입출력 가능 |

자료의 S3 특징 그림은 하나의 데이터가 여러 AZ에 복제본으로 저장되는 구조를 보여준다.

---

## 12.3 S3 구성 요소

| 구성 요소 | 설명 |
|---|---|
| 버킷 | 데이터를 저장하는 최상위 컨테이너 |
| 객체 | 버킷에 저장되는 개별 데이터 단위 |
| 키 | 버킷 안에서 객체를 식별하는 고유 이름 |
| 메타데이터 | 객체에 붙는 부가 정보 |

버킷 이름은 전 세계 AWS 사용자 전체에서 중복될 수 없고, 생성 이후 변경할 수 없다.

---

## 12.4 S3 객체 입출력

S3 객체는 HTTP 기반 API로 다룬다.

| 메서드 | 역할 |
|---|---|
| PUT | 객체를 버킷에 저장 |
| GET | 객체 조회 |
| DELETE | 객체 삭제 |
| HEAD | 객체 메타데이터 조회 |

---

## 12.5 S3 스토리지 클래스

S3는 데이터 접근 빈도와 비용 요구사항에 따라 여러 스토리지 클래스를 제공한다.

자료에 등장하는 클래스는 다음과 같다.

| 클래스 | 감각 |
|---|---|
| Standard | 자주 접근하는 일반 데이터 |
| Intelligent-Tiering | 접근 패턴이 변하는 데이터 |
| Express One Zone | 매우 빠른 접근이 필요한 단일 AZ 저장 |
| Standard-IA | 덜 자주 접근하지만 즉시 검색이 필요한 데이터 |
| One Zone-IA | 단일 AZ에 저렴하게 저장 |
| Glacier Instant Retrieval | 아카이브지만 즉시 검색 필요 |
| Glacier Flexible Retrieval | 장기 보관, 검색 시간 허용 |
| Glacier Deep Archive | 가장 저렴한 장기 아카이브 성격 |

스토리지 클래스 선택 기준은 보통 다음 세 가지다.

1. 데이터가 얼마나 자주 조회되는가?
2. 조회 속도가 얼마나 중요한가?
3. 저장 비용과 검색 비용 중 무엇이 더 중요한가?

---

## 12.6 S3 버킷 생성 실습

자료의 S3 실습 흐름은 다음과 같다.

1. 콘솔에서 S3로 이동
2. 버킷 만들기 클릭
3. 버킷 이름 입력
4. ACL 활성화 선택
5. 퍼블릭 액세스 차단 해제
6. 고지 사항 확인 체크
7. 버킷 만들기
8. 생성된 버킷 확인
9. 프론트엔드 `index.html` 파일 준비
10. EC2 백엔드 API 주소로 `API_BASE_URL` 수정

주의할 점은 S3 퍼블릭 접근 설정은 보안상 민감하다는 것이다. 실습에서는 정적 파일 공개를 위해 퍼블릭 설정을 하지만, 실제 서비스에서는 최소 공개 범위와 권한 정책을 신중하게 설정해야 한다.

## 12.7 S3 정적 웹 사이트 호스팅

S3는 정적 웹 사이트 호스팅을 지원한다.

정적 웹 사이트는 서버에서 동적으로 HTML을 생성하지 않고, 이미 만들어진 HTML/CSS/JS 파일을 그대로 제공하는 방식이다.

4. 인덱스 문서에 `index.html` 입력
5. 변경 사항 저장
6. 생성된 웹 사이트 URL 확인
7. URL로 접속 성공 확인

## 12.8 S3 프론트엔드와 EC2 백엔드 연계

자료의 실습은 S3에 프론트엔드 정적 파일을 올리고, EC2에서 백엔드 FastAPI 서버를 실행한 뒤 프론트엔드가 EC2 API를 호출하는 구조다.

구조는 다음과 같다.

```text
사용자 브라우저
  -> S3 정적 웹 사이트(index.html)
  -> JavaScript가 EC2 백엔드 API 호출
  -> EC2 FastAPI 서버 응답
```

이때 확인할 점은 다음과 같다.

| 항목 | 확인 이유 |
|---|---|
| EC2 서버 실행 여부 | 백엔드가 떠 있어야 API 응답 가능 |
| EC2 보안 그룹 8000번 포트 | 외부에서 API 호출 가능해야 함 |
| S3 index.html의 API 주소 | `localhost`가 아니라 EC2 퍼블릭 주소여야 함 |
| 브라우저 개발자 도구 Network 탭 | POST 요청 성공 여부 확인 |

# 13. AWS RDS

## 13.1 RDS란?

RDS(Relational Database Service)는 **RDBMS를 실행할 수 있는 환경을 클라우드로 제공해주는 서비스**다.

지원 엔진 예시는 다음과 같다.

- MySQL
- MariaDB
- PostgreSQL
- Oracle
- SQL Server
- Amazon Aurora

RDS는 DB 서버를 직접 설치하고 패치하고 백업하는 부담을 줄여준다.

| 기능 | 설명 |
|---|---|
| DB 설치 자동화 | DB 엔진 실행 환경 제공 |
| 유지 관리 | 패치, 백업, 복구 부담 감소 |
| 고가용성 | Multi-AZ 옵션으로 장애 대응 |
| 보안 | 네트워크 격리, 접근 제어, 암호화 지원 |

---

## 13.2 Multi-AZ

Multi-AZ는 **고가용성과 자동 장애 복구를 위한 동기식 복제 구성**이다.

| 항목 | 내용 |
|---|---|
| 복제 방식 | 동기식 복제 |
| 주요 목적 | 고가용성, 자동 장애 복구 |
| 복제 위치 | 동일 리전 내 다른 가용 영역 |
| 장애 발생 시 | 자동 페일오버 |
| 읽기 분산 목적 | 주 목적은 아님 |

동기식 복제이므로 Primary DB에 쓰기가 발생하면 Standby Replica에도 반영된 뒤 응답하는 구조로 이해하면 된다.

자료의 Multi-AZ 그림은 Primary DB가 있는 AZ에 장애가 발생하면 다른 AZ의 Standby Replica가 Active로 전환되는 구조를 보여준다.

---

## 13.3 Read Replica

Read Replica는 **조회 성능 향상과 읽기 요청 분산을 위한 비동기식 복제 구성**이다.

| 항목 | 내용 |
|---|---|
| 복제 방식 | 비동기식 복제 |
| 주요 목적 | 조회 성능 향상, 읽기 요청 분산 |
| 복제 위치 | 동일 리전의 다른 AZ 또는 다른 리전 |
| 장애 발생 시 | 수동 전환 |
| 읽기 분산 | 가능 |

Read Replica는 Primary DB의 데이터를 비동기적으로 복제하므로, 복제 지연이 발생할 수 있다. 대신 읽기 트래픽을 여러 Replica로 분산할 수 있다.

---

## 13.4 Multi-AZ vs Read Replica

| 구분 | Multi-AZ | Read Replica |
|---|---|---|
| 목적 | 장애 복구, 고가용성 | 읽기 성능 향상 |
| 복제 방식 | 동기식 | 비동기식 |
| 장애 전환 | 자동 페일오버 | 수동 전환 |
| 읽기 트래픽 분산 | 일반적으로 목적 아님 | 가능 |
| 배치 | 동일 리전 내 다른 AZ | 동일 리전 또는 다른 리전 가능 |

요약하면 다음과 같다.

```text
장애 대응이 목적이면 Multi-AZ
읽기 부하 분산이 목적이면 Read Replica
```

---

## 13.5 RDS 데이터베이스 생성 실습

자료의 RDS 실습 흐름은 다음과 같다.

1. 콘솔에서 RDS 검색
2. Aurora and RDS로 이동
3. 데이터베이스 생성
4. 전체 구성 선택
5. 엔진으로 MySQL 선택
6. 구성에서 프리 티어 선택
7. DB 인스턴스 식별자 입력
8. 마스터 사용자 이름 `root` 입력
9. 자격 증명 관리에서 자체 관리 선택
10. 마스터 암호 입력
11. EC2와 연동하기 위해 같은 VPC 사용
12. EC2 생성 시 만든 보안 그룹 선택
13. 초기 데이터베이스 이름 입력
14. 데이터베이스 생성
15. 생성 완료 후 엔드포인트와 포트 확인

RDS에 접근하려면 다음 정보가 필요하다.

| 정보 | 설명 |
|---|---|
| 엔드포인트 | DB 접속 주소 |
| 포트 | MySQL 기본값은 보통 3306 |
| 사용자 이름 | 예: `root` |
| 비밀번호 | 생성 시 지정 |
| 데이터베이스 이름 | 초기 DB 이름 |
| 보안 그룹 | EC2에서 RDS로 접근 가능한지 결정 |

EC2와 RDS를 연동하려면 네트워크와 보안 그룹 구성이 맞아야 한다. 단순히 DB를 생성했다고 바로 접근 가능한 것은 아니다.

# 17. 시험/면접식 질문으로 복습

## 17.1 네트워크

### Q1. IP와 Port의 차이는?

IP는 네트워크 상에서 호스트를 찾는 주소이고, Port는 그 호스트 안에서 실행 중인 프로세스를 찾는 번호다.

### Q2. TCP와 UDP의 차이는?

TCP는 연결 지향이며 신뢰성, 순서 제어, 오류 제어를 제공한다. UDP는 연결을 수립하지 않고 빠르게 보내지만 신뢰성은 애플리케이션이 직접 처리해야 한다.

### Q3. NAT가 필요한 이유는?

사설 네트워크의 장치가 외부 인터넷과 통신하려면 사설 IP를 공인 IP로 변환해야 하기 때문이다. 또한 여러 내부 장치가 하나의 공인 IP를 공유하는 데도 사용된다.

### Q4. CIDR에서 `/24`는 무슨 뜻인가?

IP 주소의 앞 24비트가 네트워크 부분이라는 뜻이다. IPv4 기준으로 남은 8비트가 호스트 부분이므로 일반적으로 254개 정도의 호스트 주소를 사용할 수 있다.

---

## 17.2 AWS

### Q1. VPC와 서브넷의 관계는?

VPC는 리전 단위의 독립 네트워크이고, 서브넷은 VPC 내부를 더 작게 나눈 네트워크다. AWS에서 하나의 서브넷은 하나의 가용 영역에 속한다.

### Q2. 퍼블릭 서브넷과 프라이빗 서브넷의 차이는?

퍼블릭 서브넷은 라우팅 테이블을 통해 인터넷 게이트웨이로 나갈 수 있어 외부 인터넷과 직접 통신 가능하다. 프라이빗 서브넷은 외부 인터넷과 직접 통신하지 않으며, 필요하면 NAT 게이트웨이를 통해 나가는 통신만 가능하게 만들 수 있다.

### Q3. 보안 그룹과 네트워크 ACL의 차이는?

보안 그룹은 인스턴스 수준에서 동작하는 상태 기반 방화벽이다. 네트워크 ACL은 서브넷 수준에서 동작하는 비상태 기반 방화벽이며, 규칙을 순서대로 평가하고 인바운드/아웃바운드를 각각 명시해야 한다.

### Q4. EC2에서 8000번 포트 서버를 실행했는데 외부에서 접속이 안 되는 이유는?

가능한 원인은 서버가 `127.0.0.1`에만 바인딩되어 있거나, EC2 보안 그룹에서 8000번 인바운드 포트가 열려 있지 않거나, 퍼블릭 IP/DNS가 없거나, 라우팅/인터넷 게이트웨이 구성이 안 되어 있기 때문이다.

### Q5. S3 버킷 이름이 전 세계에서 고유해야 하는 이유는?

S3 버킷은 전 세계 AWS 사용자 전체에서 식별되는 네임스페이스를 사용하기 때문이다. 따라서 같은 이름의 버킷을 중복 생성할 수 없다.

### Q6. Multi-AZ와 Read Replica는 언제 쓰는가?

Multi-AZ는 장애 발생 시 자동 페일오버를 위한 고가용성 목적이다. Read Replica는 읽기 요청을 분산해 조회 성능을 높이기 위한 목적이다.
